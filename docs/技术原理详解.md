# FixFirst 技术原理详解

**这份文档是干什么的**：FixFirst 的代码大部分由 AI 辅助写成。这份文档把数据怎么选、怎么处理、特征怎么定、规则和知识库怎么搭、推理引擎怎么实现、决策树怎么训练、效果怎么评估，按"做了什么 → 为什么这样做 → 具体怎么实现 → 例子"讲清楚，目标是让每位组员被老师追问细节时都答得上来。

**依据**：FixFirst 的代码和仓库里的实验报告。v0.6.1 于 2026-09-26 核对；9/28 起补充了难例集和 H07、H08（10.5 节）。文中的链接都指向仓库里的文件，在 GitHub 上点开就能看源码。代码改了以后，这份文档要跟着改。

**注意**：生成数据上的数字（准确率等）来自团队自己设计的场景，偏乐观。写报告、回答问题时，要和真实项目的留出结果分开讲（见第 10、11 节）。

**怎么读**：先读第 0 节的全景，再按需看各节。每节最后有"老师可能问"。最后一节把常见追问汇总在一起，附录是代码地图、规则清单和术语表。

## 0. 全景：一次排错经过哪些步骤

FixFirst 做的事可以用一句话说完：**运行项目自己的检查 → 从失败里提取证据 → 结合知识推理出根因 → 按目标排出下一步 → 用户改完代码后，用同范围的真实检查确认修好了。**

| 步骤 | 做什么 | 代码 |
|---|---|---|
| 1 检查 | 在用户选的 Python 环境里跑白名单里的检查：环境快照、项目声明和源码索引、pip check、pytest（收集 / 运行）、Ruff | [runner.py](../src/fixfirst/runner.py)、[probe.py](../src/fixfirst/probe.py)、[project.py](../src/fixfirst/project.py) |
| 2 解析与分组 | 把各工具的输出解析成"事件"，再把重复的报错归成一个"问题" | [parsers.py](../src/fixfirst/parsers.py)、[grouping.py](../src/fixfirst/grouping.py) |
| 3 证据 | 对每个问题提取证据：真实异常类型、在哪抛出、涉及的模块和 API、模块在环境和项目里的状态 | [evidence.py](../src/fixfirst/evidence.py) |
| 4 知识 | 只查证据里出现过的名字：哪个版本删了它、用什么替代、出处在哪 | [domain.py](../src/fixfirst/domain.py)、[domain.toml](../src/fixfirst/knowledge/domain.toml) |
| 5 决策树建议 | 用证据特征预测一个"可能的原因"，只作为兜底 | [classification.py](../src/fixfirst/classification.py)、[diagnosis_tree.json](../src/fixfirst/knowledge/diagnosis_tree.json) |
| 6 规则推理 | 前向链式推理：推导 → 诊断 → 经验推测 → 兜底 → 生成步骤 | [engine.py](../src/fixfirst/engine.py)、[rules.toml](../src/fixfirst/knowledge/rules.toml) |
| 7 排序 | 按"是否被挡住、对目标的影响、证据强度、步骤类型、成本"排出先后 | [reasoning.py](../src/fixfirst/reasoning.py) |
| 8 验证 | 用户改完后再检查；只有同一环境、同一范围的完整检查通过，问题才关闭 | [service.py](../src/fixfirst/service.py) |

**和课程技术的对应**（proposal 承诺至少覆盖三类）：

| 课程技术类别 | FixFirst 里对应的部分 |
|---|---|
| 决策自动化（业务规则、基于知识的推理） | 规则引擎：103 条规则，前向链式推理，带变量、分层否定、版本比较和溯源 |
| 知识表示 / 认知技术（知识图谱、面向人的界面） | 领域知识图谱（domain.toml）+ 每次会话的证据图，界面上的"为什么"就来自这里 |
| 知识发现与数据挖掘 | 决策树（Gini）根据证据特征给出可能原因；TF-IDF + 余弦相似度给重复报错分组 |
| 资源优化（部分） | "Find it" 版本搜索：在临时环境里有预算地试装旧版本（不是 A*，只算部分覆盖） |

| BugsInPy（ESEC/FSE 2020） | 公开 bug 基准 | 501 个 bug；70 个不需要编译 | 验证真实代码缺陷 | 复现脚本已写好（任务 A2） |

依据：[DATA_SOURCES.md](DATA_SOURCES.md)。

### 1.2 为什么主数据是自己生成的，而不是 PyDFix

proposal 原本写 PyDFix 是主数据源。检查它的数据表后发现三个问题：

1. **只有报错那一行，没有完整日志**，也没有环境信息。FixFirst 的很多证据（模块装没装、是不是本地文件）根本拿不到。
2. **大部分不在我们的范围内**：多是 2015–2020 年 CI 上的构建和安装失败（`setup.py`、`build_ext`），或者 Python 2.7/3.4 的版本检查。
3. 真正能读的 import 错误去重后**只剩 22 个**。

所以 PyDFix 降为小规模外部检查。主数据改成两类"能执行、能标注"的数据：自己生成的故障项目（受控、答案已知、能做均衡），加上真实开源项目（贴近现实）。

**PyDFix 仍然有用的地方**：它的论文统计了 2,702 个历史构建，其中 1,921 个（71.1%）因为依赖问题已经无法复现。这是"问题很常见"的依据，报告的商业价值部分会用到。

### 1.3 为什么 BugsInPy 只用来验证

BugsInPy 里全是**代码缺陷**，只属于五类根因中的一类，测不了 FixFirst 最核心的"环境和版本问题诊断"。而且它原本要求 Python 3.6–3.8，旧环境很难重建，所以我们统一用 Python 3.9 复现，只复现得出来的才算数。它只用来做两件事：验证修复是否被正确判断，以及检查"真正的代码 bug 不会被误判成环境问题"。先从 70 个不需要编译的候选开始，做法见任务 A2 和 `scripts/bugsinpy_case.py`。

### 老师可能问

- **为什么不用公开数据集训练？** 公开数据要么缺证据（PyDFix 只有报错行），要么只有一类原因（BugsInPy 只有代码缺陷），都不能直接训练五分类。所以训练用自己生成、真实执行的数据，真实数据留着做测试。
- **合成数据可信吗？** 它是真的建项目、真的装库、真的跑 pytest 得到的报错，不是编出来的文本；只是故障是我们注入的、比真实情况干净。这个差距用真实项目的留出测试来衡量（第 10 节）。

## 2. 215 个生成案例是怎么做出来的

代码：[diagnosis_cases.py](../src/fixfirst/diagnosis_cases.py)。

### 2.1 做法：5 个模板 × 43 个故障场景

**5 个项目模板**，每个先确认是健康的（所有测试能通过），项目布局各不相同：

| 模板 | 特点 |
|---|---|
| flat-shop | 平铺布局，模块都在根目录 |
| src-billing | src 布局，代码放在 `src/` 下 |
| pkg-inventory | 多层包（包里还有子包） |
| unittest-grades | unittest 风格的测试 |
| fixture-orders | 大量使用 pytest fixture |

**43 个故障场景**，每个只注入一个故障，标签就是场景定义里写的根因：

| 根因 | 场景数 | 例子 |
|---|---|---|
| 缺依赖（missing_dependency） | 6 | 导入一个没装的包；requirements.txt 里声明了但没装；导入名和包名不一样（`bs4` / `beautifulsoup4`） |
| 本地模块问题（local_module） | 6 | 辅助模块改了名但导入没改；包挪进 `src/` 但没加路径；项目文件和库同名把库遮住；循环导入 |
| 版本不兼容（version_incompatibility） | 13 | 用了 Python 3.12 删掉的标准库模块；`collections.Mapping`（3.10 删除）；NumPy 2.0、Jinja2 3.1 删掉的名字；scikit-learn 删掉的参数 |
| 缺配置（config_missing） | 6 | `os.environ` 里没有需要的变量；配置文件不存在；`os.getenv` 返回 None 后被使用 |
| 代码缺陷（code_defect） | 12 | 断言失败、除以零、变量名拼错、下标越界、语法错误、参数个数不对 |

每个场景套到 5 个模板上，所以 43 × 5 = **215 个案例**，分布是：版本不兼容 65、代码缺陷 60，其余三类各 30，每类都至少 30 个。

### 2.2 每个案例怎么生成

1. 复制一个健康的模板；
2. 注入一个故障，比如在代码里加一行 `from collections import Mapping`；
3. **在真实的 Python 环境里真的运行**环境快照、项目检查和 pytest，库是实际装的版本（Python 3.12.14、NumPy 2.5.3、scikit-learn 1.9.0 等），**没有任何模拟（mock）**；
4. 把这次运行的完整会话记录下来。

注入的故障都真的出现了，0 个案例因为"故障没表现出来"而被剔除。

### 2.3 两个刻意的设计

- **故意让知识库不全**：43 个场景里只有 14 个（70 个案例）是知识库收录了的；另外 29 个（145 个案例）用的是知识库里**故意没写**的删除项或配置模式，比如知识库里没有的 NumPy 删除函数。这样才能测出"知识库没覆盖时系统怎么办"，也能公平地比较规则和决策树。
- **成对的"长得像、原因不同"**：比如同样是 KeyError，一个是读 `os.environ` 失败（缺配置），一个是查数据字典失败（代码缺陷）。这正是"报错一样、原因不同"的受控版本。

### 2.4 局限

每个案例只有一个故障、只有 5 个模板，比真实项目干净得多。真实项目往往一层套一层，比如 Flask 1.1.4 修完一层才暴露下一层。所以合成数据上的成绩一定偏高，必须用真实项目的留出测试来校正。

### 老师可能问

- **标签是谁标的？** 生成案例不需要人工标注：注入什么故障，标签就是什么，写在场景定义里，不来自 FixFirst 的规则或模型。
- **为什么每类至少 30 个？** 让五类大致均衡。真实故障高度偏向版本问题，如果训练数据也偏，模型全猜"版本不兼容"准确率也不低，但毫无用处；所以同时报告 Macro-F1 和分类别结果。
- **能不能多生成一点？** 能，生成是脚本化的（约 2 分钟跑完 215 个）。但简单地多造同类案例意义不大；接下来要加的是更像真实情况的场景，比如多层故障、插件行为变化。

## 3. 数据处理：从运行输出到"证据"

### 3.1 检查是怎么跑的

- **只跑白名单里的检查**：环境快照、项目检查、pip check、pytest 收集、Ruff；用户目标是"让测试通过"时再加完整的 pytest 运行；用户点 Find it 时才做版本搜索。
- **安全措施**：参数直接交给子进程，不经过 shell；每个检查 10 分钟超时、输出上限 1 MB，超时杀掉整个进程组；输出会脱敏（密码、token、`os.environ` 的内容都会被替换）。
- **像激活了虚拟环境一样跑**：环境的 `bin` 目录放在 PATH 最前面。这是第 1 轮真实项目测试后加的：attrs 的测试要调用 `mypy` 命令，不激活环境就找不到。
- **环境快照和 pip check 在临时目录里跑**，避免项目里一个叫 `random.py` 的文件把标准库遮住，导致检查本身出错。

### 3.2 pytest 探针：为什么不直接读 pytest 的文字输出

pytest 打印出来的文字格式不稳定、信息也不全，比如收集阶段的错误会被包成 `CollectError`，看不到真实的异常类型。所以 FixFirst 带了一个很小的 pytest 插件（[probe.py](../src/fixfirst/probe.py)），测试运行时直接记录结构化信息：

- 真实的异常类型和信息；
- 最内层的调用帧，以及实际执行到的源码行；
- 涉及的模块名、API 名、关键字参数名、配置键、缺失的文件、缺失的 fixture；
- 测试失败时记录下来的警告，以及每条警告是在哪里产生的。

探针被复制到一个临时目录里加载，在目标环境里只用标准库，不会给用户环境装任何东西。

### 3.3 解析和分组

**解析**：把 pip、pytest、Ruff 等工具的输出转成统一的"事件"。看不懂的输出也会保留，**绝不把"没看懂"当成"没问题"**。

**分组**：同一个原因常常造成很多条报错，比如一个缺失的包让 20 个测试文件都导入失败。分组就是把它们归成一个问题。做法分两步：

1. **结构分块**：只有工具、阶段、事件类型、组件和报错里的版本号字符串都相同的事件，才可能分到一组。
2. **块内比较文本相似度**：
   - 先把文本规范化：去掉颜色码、时间戳、临时路径、内存地址；
   - 用 TF-IDF 把报错文本变成向量，以字符为单位、长度 3–5 的片段；
   - 算两两之间的余弦相似度；
   - 用**完全链接（complete-link）**合并：一组里任意两条的相似度都 ≥ 0.82 才能进同一组，避免 A 像 B、B 像 C 就把 A 和 C 硬凑一起的"链式合并"。

阈值 0.82 是事先定的，没有用测试数据调过。

**说实话的部分**：目前 TF-IDF 分组在受控数据上和"完全相同才合并"一样好（两者都是 1.0），在真实数据上也没有差别（235 个事件，两种方法都分成 219 组）。原因是结构分块已经把大部分事件分开了，每个失败的测试基本自成一块。这部分正在改进（任务 B9）：用路径、行号、数值不同的重复报错做更难的测试集，报告 precision、recall 和 F1。

### 3.4 证据提取

对每个问题，[evidence.py](../src/fixfirst/evidence.py) 汇总出：

- **错误本身**：异常类型、失败阶段（收集 / 准备 / 运行 / 清理）、报错信息里的关键说法；
- **在哪里抛出**：项目代码、测试代码、第三方库、标准库，以及调用栈里第三方库的帧占多少；
- **模块在环境和项目里的状态**，这部分是区分根因的关键：
  - 装了没有：查环境快照里"导入名 → 发行包"的对应关系；
  - 是不是标准库：查 `sys.stdlib_module_names`，老版本 Python 有后备办法；
  - 是不是项目里的本地文件：查项目的源码索引；
  - 有没有名字很像的本地文件：用 `difflib` 找相似度 ≥ 0.75 的文件名，用来发现"改名了"；
  - 有没有在依赖里声明：读 requirements 文件、`pyproject.toml`（包括 poetry 和老版 flit）、`setup.cfg`，以及 `setup.py`（只做静态语法分析，**从不执行**）。

同一份证据会变成两种形式：**给规则用的事实三元组**（第 6 节），和**给决策树用的特征向量**（第 4 节）。

### 老师可能问

- **一次失败会不会被数成好几个问题？** 分组就是为了避免这个。真实项目测试里还发现过一种情况：报错里点名了缺失的名字时，同一行 import 的其他名字不能也算缺失。这是第 1 轮后修的通用问题之一。
- **分组阈值怎么定的？** 事先定为 0.82，没有在测试数据上调参。

## 4. 特征：44 个是怎么定的

代码：[evidence.py](../src/fixfirst/evidence.py) 里的 `FEATURE_NAMES` 和 `features()`。

### 4.1 设计原则

**特征是人工设计的，不是从数据里自动学出来的。** 设计方法很朴素：一个有经验的人排查"为什么导入失败 / 为什么报错"时会问哪些问题，就把这些问题做成特征。每个特征都和区分五类根因直接相关。

| 组 | 个数 | 内容 |
|---|---|---|
| 异常类型 | 12 | 11 种常见异常各占一个（ModuleNotFoundError、ImportError、AttributeError、KeyError、FileNotFoundError、TypeError、AssertionError、RuntimeError、ValueError、NameError、SyntaxError），再加"其他" |
| 失败阶段 | 4 | 收集、准备（setup）、运行（call）、清理（teardown） |
| 在哪抛出 | 6 | 项目代码、测试代码、第三方库、标准库、未知，加一个"第三方库帧的占比" |
| 模块状态 | 9 | 报错提到模块了吗、装了吗、是标准库吗、是本地文件吗、有相似名字的本地文件吗、声明了吗、缺的是带点的子模块吗、提到 API 了吗、出错的对象是项目自己定义的吗 |
| 文字信号 | 13 | 报错信息里有没有这些说法："no attribute"、"cannot import name"、未知关键字参数、读 `os.environ`、`getenv`、NoneType、配置相关的词、配置文件、配置上下文、文件不存在、循环导入（partially initialized）、相对导入、"removed / deprecated / no longer" 之类 |

合计 44 个：43 个是/否特征，加 1 个 0 到 1 之间的比例。9/28 pre 的幻灯片上写"约 40 个是/否特征"是简化说法。

### 4.2 几个特征为什么有用（举例）

- **"装了吗" + "声明了吗"**：没装但声明了 → 缺依赖（该装的没装）；没装、没声明、但有相似名字的本地文件 → 更像本地模块改名了。
- **"是标准库吗" + 异常类型**：标准库里找不到、又是 ModuleNotFoundError → 可能是新 Python 删了这个模块（版本不兼容）。
- **"读 `os.environ`" 信号**：同样是 KeyError，读 `os.environ` 失败是缺配置，查普通字典失败是代码缺陷。
- **"出错的对象是项目自己定义的吗"**：AttributeError 发生在项目自己的类上，多半是拼错了（代码缺陷），而不是库的版本问题。

### 4.3 故意不放进来的东西

**解析器给的报错分类和标签，一律不当特征。** 解析器会先给每个报错一个粗分类（比如"依赖问题"），这个分类几乎就是答案。放进去的话，决策树照抄就能"答对"，准确率很好看，其实什么也没学到，这叫**标签泄漏（label leakage）**。早期的 v0.3 就是这么做的，v0.4 起改掉了。代码里的 `naive_diagnosis` 保留了 v0.3 的做法，只当作对比基线。

### 4.4 特征数量为什么固定

特征是在代码里写死的，数量不随数据变化。要加一个特征，得改代码、重新训练。训练出来的模型文件里记着特征名单，和代码对不上时 FixFirst 会拒绝加载，防止"模型和特征对不上"这类隐蔽错误。

### 4.5 实际用上了多少

最终那棵树只在 **14 个特征**上做了分裂。重要性最高的几个是：
- 报错提到模块了吗 0.23
- 提到 API 了吗 0.19
- 是本地文件吗 0.13
- 有配置上下文吗 0.10
- 有相似名字的本地文件吗 0.06
- 在测试代码里抛出 0.05
- 读 `os.environ` 0.05
- 配置文件 0.04

也就是说，"哪些特征有用"是树在训练时自己挑的，另外 30 个在目前的数据上没派上用场。这也说明合成数据主要靠"模块状态"就能区分，真实数据更复杂时，其他特征才可能发挥作用。

### 老师可能问

- **为什么不用深度学习或者直接把报错文本丢给模型？** 数据量小（215 个），需要结果能解释；人工特征能把环境信息（装没装、声明没有）带进来，这些信息光看报错文本是没有的。
- **特征有没有做选择？** 没有单独做特征选择；决策树训练时会自己挑分裂特征，结果只用到 14 个。
- **会不会有冗余？** 有，在当前数据上 30 个没用上。保留它们是为了让模型以后在更多样的数据上有东西可用。

## 5. 知识库（领域知识图谱）

代码：[domain.toml](../src/fixfirst/knowledge/domain.toml)（数据）、[domain.py](../src/fixfirst/domain.py)（读取和查询）。

### 5.1 里面有什么

知识库是一个 TOML 数据文件，全部是"事实 + 出处"：

| 内容 | 数量 | 用途 |
|---|---|---|
| 五类根因的定义 | 5 | 统一的分类 |
| 报错类型 → 可能的根因 | 8 条 | 比如 ModuleNotFoundError 可能是缺依赖、本地模块或版本问题 |
| 导入名 → PyPI 包名 | 42 个 | 比如 `cv2` 对应 `opencv-python`、`bs4` 对应 `beautifulsoup4` |
| 被删除的名字（模块、API、属性、参数、用法、fixture） | 27 组共 119 个，覆盖 12 个发行包 | Python 3.10–3.13、NumPy、SciPy、scikit-learn、pandas、Jinja2、MarkupSafe、Werkzeug、packaging、pydantic、pytest、pytest-asyncio |
| 即将删除（已弃用）的名字 | 10 个 | 预警：现在只是警告，以后会坏 |
| pytest fixture → 提供它的插件 | 44 个 fixture，21 个插件 | 比如 `benchmark` 由 pytest-benchmark 提供 |
| 不再维护的包 | 1 个（nose） | 没有新版本可升级时，建议换掉 |
| Ruff 里通常代表 bug 的规则 | 一组 | 把代码检查结果分成"可能是 bug"和"只是风格" |
| 引用来源 | 23 个 | 每条事实都指向一个来源的标题和网址 |

**例子**（pre 上讲过的那条）：

```toml
[[removed]]
kind = "api"
module = "collections"
names = ["Mapping", "MutableMapping", "Sequence", ...]
distribution = "python"
version = "3.10"
replacement = "the same names from collections.abc"
source = "python-3.10"

[sources."python-3.10"]
title = "What's New In Python 3.10 (removed collections ABC aliases)"
url = "https://docs.python.org/3/whatsnew/3.10.html"
```

### 5.2 为什么叫"知识图谱"

这些条目可以看成节点和关系：报错类型 →（可能意味着）→ 根因；导入名 →（属于）→ 发行包；某个 API →（从……删除）→ Python；某个 API →（记载于）→ 某份文档。`fixfirst knowledge --output kg.json` 可以把它连同规则导出成图。推理时，这些关系会变成事实三元组，交给规则去匹配。

### 5.3 怎么用：只查证据里出现过的名字

`domain.facts_for` 拿到证据里出现的名字（比如 `collections.Mapping`），只查这些名字，生成对应的知识事实：

- `(collections.Mapping, removed_from, python)`
- `(collections.Mapping, removed_in_version, 3.10)`
- `(collections.Mapping, replacement, collections.abc 里的同名类)`
- 每条都带着出处 `python-3.10`

这些事实和证据事实、环境事实（比如 `python` 装的是 3.12.14）放在一起，交给推理引擎。

### 5.4 怎么建、怎么维护

- 从官方 release notes 和文档手工整理，**每条都必须写出处**；加载时会检查类型是否合法、出处是否存在。
- 扩展知识就是加一条记录。比如 Python 3.14 删了什么，照格式加一组，写上 What's New 的链接即可，不用改代码。
- 缺点是覆盖面有限，要人维护。所以有决策树兜底：知识库没写的情况，树还能根据证据给出"可能的原因"。

### 5.5 效果（生成数据上的数字）

在知识库覆盖的故障上（70 个案例）：
- 只看规则：有知识库时 100% 正确，去掉知识库只剩 7%；
- 规则 + 决策树：去掉知识库后从 100% 降到 64%。

说明知识库是规则能起作用的前提。

### 5.6 证据图

除了静态的知识库，每次会话还会建一个**证据图**（[knowledge_graph.py](../src/fixfirst/knowledge_graph.py)）：
- **节点和关系**：10 类节点（目标、行动、问题、原因、事实、规则、事件、证据、运行、来源），15 种关系。
- **用途**：界面上"为什么先做这一步""这个结论依据什么"都是沿着这张图找到的。
- **问答**：能回答少量固定类型的中英文问题，比如"为什么要做这一步""是什么挡住了目标"；不支持的问题会直接拒绝，不瞎猜。

### 老师可能问

- **知识库怎么保证正确？** 每条都来自官方文档并附链接，可以逐条核对；加载时校验格式和出处。
- **Python 出新版本怎么办？** 按 What's New 加条目即可，不用改代码；没来得及加的，由决策树兜底，结论标为"未确认"。
- **为什么不用现成的知识图谱（比如 Wikidata）？** 没有现成的图谱记录"哪个库哪个版本删了哪个名字"这种细粒度的事实，只能自己从 release notes 整理。

## 6. 规则库

代码：[rules.toml](../src/fixfirst/knowledge/rules.toml)。

### 6.1 规则长什么样

规则也是 TOML 数据，不是代码。每条规则包括：
- 编号、所属阶段、一句话说明、出处；
- **when**：条件；
- **then**：得出的新事实；plan 阶段的规则换成 **action**，也就是一个行动模板。

条件有三种写法：

| 写法 | 例子 | 意思 |
|---|---|---|
| 事实 | `["?i", "api", "?x"]` | 必须有一条事实能对上；`?x` 这类变量第一次出现时绑定成具体值，后面再出现必须相等；`?_` 表示任意值 |
| 否定 | `["not", "?i", "diagnosis", "?_"]` | 找不到这样的事实才成立（否定即失败） |
| 比较 | `["test", "version_gte", "?iv", "?v"]` | 内置比较：版本 ≥、版本 <、大版本更高、在列表里、不在列表里、等于、不等于 |

**诊断规则例子 D02**：

```toml
[[rule]]
id = "D02"
phase = "diagnose"
description = "The code uses a module attribute or imported name that the installed version no longer provides."
when = [
  ["?i", "api", "?x"],                                                  # 问题 i 用到了名字 x
  ["?x", "removed_from", "?d"], ["?x", "removed_in_version", "?v"],     # 知识库：x 在 d 的 v 版被删
  ["?d", "installed_version", "?iv"], ["test", "version_gte", "?iv", "?v"],  # 装的版本 ≥ v
]
then = [["?i", "diagnosis", "version_incompatibility"], ["?i", "remedy", "replace_removed"], ["?i", "because", "?x"]]
```

**经验推测例子 H01**：从已安装的第三方库里 import 某个名字失败，而这个模块不是项目自己的文件、也还没有确定的诊断，那么**很可能**是版本变化导致的。结论写成 `likely`，界面上显示为"未确认"。

**兜底例子 F01**：既没有诊断结论，也没有经验推测时，采用决策树的建议，结论写成 `suspected`（未确认）。

**生成步骤例子 P09**：如果被删的 API 所属的库，是另一个已安装的包要求用旧版本的，那就不该改代码，而是装回那个包要求的版本。它的标题模板是：

```text
Install the {?d} version that {?who} requires ({?spec})
```

其中 `{?d}` 等占位符用匹配时绑定的值填进去。

### 6.2 五个阶段各干什么

| 阶段 | 条数 | 作用 | 例子 |
|---|---|---|---|
| 推导 derive | 10 | 判断问题和目标的关系，生成辅助事实 | G05：收集阶段出错会挡住"运行测试"这个目标，必须先修 |
| 诊断 diagnose | 34 | 有确凿证据时得出根因 | D02 版本删除、D13 src 布局没加路径、D30 缺环境变量 |
| 经验推测 heuristic | 8 | 没有确定结论时，按常见经验给出"可能的原因" | H01 库版本变化、H04 缺了未知插件、H07 库函数拒绝了参数 |
| 兜底 fallback | 1 | 前两阶段都没结论时，用决策树的建议 | F01 |
| 生成步骤 plan | 50 | 把结论变成具体的一步：说明、命令、怎么确认 | P09、P10 替换删除的 API、P17 装缺的包、P62 退回声明的大版本 |

诊断规则的编号有规律：D0x 版本不兼容，D1x 本地模块，D2x 缺依赖和缺插件，D3x 缺配置，D4x 代码和测试本身的问题。全部规则见附录 B。

### 6.3 规则是怎么写出来的

- **来自官方文档的条件**：比如"装的版本 ≥ 删除它的版本"就是 release notes 的直接推论。
- **来自排错经验**：比如 src 布局、同名文件遮住库、循环导入，都是常见的坑。
- **来自真实项目演练**：H01/H02 是 humanize 和 Flask 演练之后加的；第 1 轮真实项目测试暴露的通用问题（第 10.3 节）也促成了几条新规则。
- **有单元测试覆盖**：推理链、循环、多条件连接、被拒绝的否定等情况都有测试；规则库加载时还会做一致性检查（第 7.4 节）。

### 6.4 多条规则都成立怎么办

- **阶段本身就是优先级**：经验推测和兜底规则的条件里写着 `not diagnosis`，只要诊断阶段已经有结论，它们就不会触发。
- **生成步骤时会合并**：同一个行动（比如"安装某个包"）被多个问题需要时，只生成一步，并记下它对应哪些问题。
- **最后统一排序**：由第 9 节的排序规则决定谁在前，依据充分的步骤排在猜测之前。

### 6.5 效果（生成数据上的数字）

在 215 个生成案例上，规则 + 知识库对 79% 的案例给出了答案，给出的答案 100% 正确；加上经验推测后能答 83%，仍然 100% 正确。规则的特点是"不确定就不说，说了就对"，剩下的交给决策树。

### 老师可能问

- **规则是看着测试数据写的吗？** 生成数据的场景是团队自己设计的，规则写的时候知道有哪些场景，所以规则在生成数据上的成绩偏乐观。正因如此：一是故意留了 145 个知识库没覆盖的案例；二是真实项目的测试必须用新选的项目，标签在跑之前写好。
- **103 条规则会不会互相冲突？** 靠阶段顺序和 `not` 条件避免；加载时的分层检查保证否定条件不会读到"还没算完"的结果（第 7.4 节）。

## 7. 推理引擎是怎么实现的

代码：[engine.py](../src/fixfirst/engine.py)，约 280 行纯 Python。没有用 CLIPS、Drools 这类现成的规则引擎，只借用 `packaging` 库来比较版本号。规则是数据，引擎是通用的，不含任何具体的诊断知识。

### 7.1 事实：三元组

每条事实是（主语，谓词，值），比如：
- `(issue-7, api, collections.Mapping)`：这次失败用到了这个名字，来自证据；
- `(collections.Mapping, removed_in_version, 3.10)`：来自知识库；
- `(python, installed_version, 3.12.14)`：来自环境快照。

每条事实还记着四项信息：
- **状态**：观察到的 / 推出来的 / 猜测的；
- **来源规则**：由哪条规则推出；
- **输入事实**：由哪几条事实推出；
- **证据引用**：依据哪次检查的记录。

事实存在 `FactBase` 里，**按谓词建了索引**：匹配 `removed_in_version` 时只看这一类事实。重复的事实不会加第二次。

### 7.2 匹配：回溯搜索

`matches` 从左到右逐条检查规则的条件：
1. 对"事实"条件，拿它和同谓词的事实逐个比对（`unify`）。变量没绑定就绑定，已经绑定就必须相等。
2. 比对成功，就带着新的绑定去检查下一条；失败就回退，换下一个事实。
3. "否定"条件：在当前绑定下找不到匹配的事实才算成立。
4. "比较"条件：用已经绑定的值直接计算。

每找到一组让所有条件都成立的绑定，就产出一次规则实例。原理和 Prolog / Datalog 的查询一样。

### 7.3 运行：分阶段推到不动点

`run` 按固定顺序执行：推导 → 诊断 → 经验推测 → 兜底。每个阶段内部：

1. 把本阶段的所有规则，对所有能匹配上的绑定都执行一遍；
2. 把结论实例化成新事实加进去，同时记下来源规则、输入事实和证据引用；
3. 只要这一轮加了新事实，就再来一轮；一整轮下来什么都推不出时，就到了**不动点**，进入下一阶段。

plan 阶段单独处理（`propose`）：它不加事实，而是把行动模板里的 `{?var}` 用绑定值填好，生成具体步骤；同一个行动被多个问题需要时合并成一个。

### 7.4 三个保证正确性的设计

- **一定会停**：规则的结论只能用规则里写的常量和已经绑定的值，不会凭空造出新值，所以可能的事实是有限的，推理一定会停。另外设了 2 万条事实的上限作保险。
- **分层否定（stratified negation）**：加载规则时会检查，`not` 只能否定**更早阶段**才会得出的谓词。比如兜底规则 F01 写着"没有诊断结论"且"没有经验推测"，这两类结论分别在诊断和经验推测阶段产生，都比兜底早。到兜底阶段时，它们已经是最终结果，不会出现"判定没有诊断、后面又冒出一个诊断"的矛盾。
- **变量安全**：比较条件和结论里用到的变量，必须先在某个事实条件里被绑定过，否则规则库加载失败。另外还检查：编号不重复、阶段名合法、只有 plan 规则能生成行动。

### 7.5 "猜测"会一路传下去

如果规则本身标为猜测（经验推测、兜底），或者用到的任何一条事实是猜测（比如决策树的建议），推出来的结论也标为猜测。界面上的 "Possible cause · not confirmed" 就是这么来的。

### 7.6 溯源：界面上的"为什么"

每条推出来的事实都记着"哪条规则、用了哪些事实、依据哪些检查记录"。所以界面 Details 里能显示 "Rule D02" 和 "Source: What's New In Python 3.10"，证据图也能一路追到原始的检查输出。

### 7.7 在整个流程里怎么被调用

`reasoning.infer_and_plan` 的顺序是：

1. 把检查结果转成**证据事实**；
2. 只对证据里出现过的名字查**知识库**；
3. 加上相关发行包的**已安装版本**；
4. 决策树置信度 ≥ 0.6 时，加一条**猜测事实** `model_suggests`；
5. 引擎分阶段推到不动点；
6. 生成行动，加上"重新检查"类的验证步骤，然后**排序**。

### 7.8 collections.Mapping 例子的完整推理过程

- **证据**：`(issue-7, api, collections.Mapping)`，来自 pytest 探针；
- **知识**：`(collections.Mapping, removed_from, python)`、`(collections.Mapping, removed_in_version, 3.10)`；
- **环境**：`(python, installed_version, 3.12.14)`；
- **匹配 D02**：`?i = issue-7`、`?x = collections.Mapping`、`?d = python`、`?v = 3.10`、`?iv = 3.12.14`；比较 `3.12.14 ≥ 3.10` 成立；
- **加入新事实**：诊断 = 版本不兼容；补救 = 替换这个名字；原因 = `collections.Mapping`，都记着"来自 D02"；
- **plan 阶段**：P10 生成步骤 "Replace collections.Mapping: removed in Python 3.10"，附上替代方法和确认方式；
- **兜底不触发**：H01、F01 的条件里有 `not diagnosis`，已经有诊断了，所以不会触发。

### 老师可能问

- **为什么用前向链，而不是后向链？** 排错时事先不知道要问什么，是从观察到的证据出发，把能推出的结论都推出来，这是数据驱动，适合前向链。后向链适合"验证某一个假设成不成立"。
- **为什么不用 Rete 算法？** 规模小：每次几十个问题、几百到几千条事实，朴素的回溯匹配加谓词索引已经够快。Rete 适合规则多、事实频繁变化的大系统。
- **规则会不会死循环？** 不会：不产生新常量，事实有限，所以一定到达不动点；另外有 2 万条的上限。
- **否定怎么处理？** 否定即失败，并按阶段分层，加载时检查（见 7.4）。

## 8. 决策树

代码：[classification.py](../src/fixfirst/classification.py)。训练结果：[decision_tree.txt](../examples/diagnosis-evaluation/decision_tree.txt) 是可读的树，[REPORT.md](../examples/diagnosis-evaluation/REPORT.md) 是实验报告。

### 8.1 为什么选决策树

- 数据量小，只有 215 个；
- 特征基本都是是/否，决策树处理起来很自然；
- **能解释**：整棵树可以打印成一串 if-else 看清楚；
- Gini 决策树是课程里讲过的方法。

### 8.2 怎么训练

- 用 scikit-learn 的 `DecisionTreeClassifier`：`criterion="gini"`、`max_depth=6`（最多 6 层）、`min_samples_leaf=2`（每个叶子至少 2 个样本）、`random_state=42`（结果可复现）。
- 超参数**事先定死**，没有用测试数据调。
- 训练数据：215 个生成案例的 44 维特征向量 + 标签。
- 训练完导出成 JSON：每个节点记着用哪个特征、阈值、左右子节点，叶子记着各类的样本数。所以 FixFirst 运行时**不需要装 scikit-learn**，`predict_tree` 沿着 JSON 走到叶子就行。
- **置信度** = 叶子里最多那一类所占的比例。

### 8.3 训练出来的树

- 17 个叶子，16 次分裂，用到 14 个特征；
- 根节点问的是"报错里有没有提到某个模块"；
- 重要性前几名见 4.5 节。

### 8.4 在系统里的位置：只做兜底

- 置信度 ≥ 0.6 的建议才会变成一条"猜测"事实，低于这个值不显示。0.6 是代码里固定的阈值，没有在测试数据上调过；后续可以用验证集校准。
- 只有诊断和经验推测**都没有结论**时，F01 才采用它，结论标为"未确认"。
- 对应的步骤（P30）排在所有有证据的步骤后面。

### 8.5 为什么不单独用决策树（生成数据上的数字）

在"没见过的故障类型"上（留一个场景交叉验证，见 10.1）：

| 方法 | 准确率 |
|---|---|
| 只用决策树 | 61% |
| 规则 + 知识库 + 经验推测 | 83%（答了的都对） |
| 全部组合（FixFirst） | 93% |

决策树的价值在知识库没覆盖的故障上：这 145 个案例里，加上决策树后准确率从 74.5% 提到 89.7%。三者各管一块：
- **规则**：精确，但只在有知识的地方有效；
- **决策树**：能覆盖没写进知识库的情况，但错得更多；
- **知识图谱**：既给规则提供事实，也给用户提供解释。

### 老师可能问

- **会过拟合吗？** 有三道防线：深度限制在 6 层、每个叶子至少 2 个样本，并且用两种交叉验证评估，每一折都重新训练（第 10 节）。在"没见过的故障类型"上单独用树只有 61%，这个诚实的数字本身就说明它确实会犯错，所以才只让它兜底。
- **为什么不用随机森林、神经网络？** 数据少，而且要解释给用户看；一棵树能直接打印出来。以后数据多了可以比较随机森林，但可解释性会下降。
- **为什么只用合成数据训练？** 见第 1 节：真实项目少、分布偏，还要留着做诚实的测试。
- **置信度 0.6 怎么来的？** 是事先设定的保守阈值，没有在测试集上调过。

## 9. 排序和验证：怎么"证明修好了"

### 9.1 下一步怎么排序

`reasoning.order_actions` 按以下顺序比较：

1. **前提是否满足**：前提还没满足的步骤排后面，比如"先拍环境快照才能判断"；
2. **对目标的影响**：影响或挡住当前目标的排前面。比如收集阶段出错时，测试根本跑不起来，所以先修收集错误；
3. **证据强度**：有知识支撑 3 > 有证据 2 > 通用建议 1 > 猜测或待验证 0；
4. **步骤类型**：先收集证据，再修复，最后重新检查；
5. **成本**：便宜的在前；
6. 编号（保证排序稳定）。

**用户目标**有三种，决定"什么算挡住目标"：
- 让测试通过（Make my tests pass）→ 完整跑测试；
- 只要测试能加载 → pytest 收集；
- 通过代码检查 → Ruff。

### 9.2 什么时候才算"修好了"

这是 FixFirst 和普通工具最不一样的地方：

- 用户改完代码点 Check again，下一次检查**只更新它覆盖到的问题**；
- 完整的 pip check 或 Ruff 运行、输出有效、并且不再报告某个问题 → 这个问题关闭；
- 完整的测试运行会关闭之前的收集错误；
- 以下情况**都不能**关闭问题：导入的旧日志、只重跑了一部分、测试被跳过或标记为 xfail、测试被删掉、放宽了依赖声明、换了一个 Python 解释器；
- 目标状态"已达成"要求：最近一次对应检查是真正执行过的（不是导入的）、覆盖整个项目、在同一个环境里、并且通过了。

### 9.3 版本搜索（Find it）

当一个库里找不到代码要用的名字，规则最多只能说"旧版本可能有"。用户点 Find it 后，[versions.py](../src/fixfirst/versions.py) 会：

1. 从 PyPI 读出版本列表，只保留有适合当前 Python 的预编译包的稳定旧版本；
2. 在一个临时环境里试装，先按倍数往前跳，再用二分法缩小范围，**最多试 12 次**；
3. 找到仍然提供这个名字的版本后，规则 D09 和 P57 给出精确的版本号（`==`）。

用户自己的环境不会被改动。这算"有预算的搜索"，不是 A*，所以只算部分覆盖第四类技术。

### 老师可能问

- **一个项目有好几个故障怎么办？** 按目标排序，先修挡住目标的（比如收集错误）；修完再检查，往往会暴露下一层问题，计划随之更新。样例项目（Open a sample project）就是这样：修完两个导入问题后，才出现两个运行时问题。
- **规则和决策树都给不出原因怎么办？** 给出收集更多证据的通用步骤（比如 P40、P50），不会编造原因。

## 10. 评估：怎么证明有效

### 10.1 生成数据上的实验

依据：[REPORT.md](../examples/diagnosis-evaluation/REPORT.md)。

**两种交叉验证**：
- **留一个模板（LOTO，5 折）**：用 4 个模板训练，测第 5 个，看"没见过的项目结构"；
- **留一个场景（LOSO，43 折）**：用 42 个故障场景训练，测剩下那个，看"没见过的故障类型"。

每一折都重新训练决策树；规则和知识库是固定的，不参与训练。

**比较 7 种方法**：
1. 只看解析器的分类（v0.3 的做法，作基线）；
2. 只用规则，不用知识库；
3. 规则 + 知识库；
4. 规则 + 知识库 + 经验推测；
5. 只用决策树；
6. 规则 + 经验推测 + 决策树，不用知识库；
7. 全部组合（FixFirst）。

**指标**：
- 准确率，带 bootstrap 95% 置信区间；
- Macro-F1：五类各算 F1 再平均，避免大类掩盖小类；
- 覆盖率：给出答案的比例（规则没把握时可以不答）；
- 回答时的精确率：只看给出答案的那部分对了多少。

**主要结果（LOSO，没见过的故障类型）**：

| 方法 | 准确率 | Macro-F1 | 覆盖率 | 回答时精确率 |
|---|---|---|---|---|
| 只看解析器分类（v0.3 基线） | 0.419 | 0.280 | 1.000 | 0.419 |
| 规则，不用知识库 | 0.488 | 0.603 | 0.512 | 0.955 |
| 规则 + 知识库 | 0.791 | 0.887 | 0.791 | 1.000 |
| 规则 + 知识库 + 经验推测 | 0.828 | 0.902 | 0.828 | 1.000 |
| 只用决策树 | 0.609 | 0.571 | 1.000 | 0.609 |
| 规则 + 经验推测 + 决策树，不用知识库 | 0.814 | 0.821 | 1.000 | 0.814 |
| 全部组合（FixFirst） | **0.930** | **0.930** | 1.000 | 0.930 |

**为什么 LOTO 上全部组合是 100%，却不能当成绩讲？** 同一个故障场景在 5 个模板里都出现了，留出一个模板时，树在训练中已经见过这种故障。所以 LOTO 太乐观，诚实的数字是 LOSO 的 93%。

**最难的场景**：
- 数据字典的 KeyError（cd_dict_key）、fixture 里的数据错误（cd_fixture_bug）：规则和树都答错。v0.3 基线反而答对，因为它把认不出的都默认算成代码缺陷。
- 知识库没收录的库子模块被删（vi_unknown_submodule）：所有方法都答错。

### 10.2 上游回归缺陷

packaging 和 click 的 4 个真实 bug（[REPORT.md](../examples/historical-regressions/REPORT.md)）：测试代码不变，在全新的隔离环境里离线安装官方发布包，从有 bug 的版本换到修复版本。4 个都复现了：坏版本退出码 1，修复版本退出码 0。这验证的是"换版本后问题是否真的消失"这个判断。

### 10.3 真实项目

**演练**（[REAL_PROJECTS.md](REAL_PROJECTS.md)）：Flask 1.1.4 装上今天的依赖库后，一个测试都跑不起来；按 FixFirst 的建议一层层修，最后 525 个测试通过。

**13 个项目的留出检查**（[GENERALISATION.md](GENERALISATION.md)）：
- **第 1 轮（留出）**：第一步完全正确 2 个，部分正确 3 个，太笼统 3 个，错误 5 个；根因说对了 6 个。和合成数据上的 93% 差距很大：真实项目难得多。
- **第 1 轮暴露的问题都是通用的，不针对某个项目**：
  - FixFirst 自己的兼容性问题：Python 3.9 缺某些接口、pytest 9 的子测试记录太多、测试没在激活的环境里跑；
  - 证据读错：一个缺失的名字被数成好几个问题，看不懂启动时崩溃的 traceback；
  - 依赖声明没读到：`setup.py` 和老版 flit 的声明；
  - 建议不对：让 pip 去"安装旧版 Python"，退回的版本跨度不合适；
  - 证据够不着的情况：行为变了但不报错。
- **第 2、3 轮**：修了这些通用问题后是 12/13，但这**不算留出成绩**，因为已经看过这些项目；另外有两条知识（nose 不再维护、pytest-asyncio 1.0 删了 `event_loop`）是看了第 1 轮之后才加的。
- 所以正式测试要**另选 10–15 个新项目**，先写标签，冻结版本，只跑一次（任务 A1、C1、A3）。

### 10.4 分组

见 3.3 节：受控数据上 TF-IDF 和完全匹配都是 1.0，真实数据上没有差别，需要更难的测试集。

### 10.5 难例集：库的行为变了（9/28 新增）

**为什么做**：第 1 轮真实项目里，唯一没修掉的一类错误是"库的行为变了，但不报'名字被删'的错"（第 11 节第 3 条）。试调研 12 个失败项目里有 3 个属于这类。

**怎么做**（`hard_cases.py`，`fixfirst dataset --suite hard`）：用环境里真实装着的库，挑有官方文档记载的变化，全部真实运行，不做模拟：

| 场景 | 变化 | 报错长什么样 |
|---|---|---|
| vb_numpy_repr | NumPy 2 标量的 repr 变成 `np.float64(2.0)`（NEP 51） | 测试里字符串断言失败 |
| vb_numpy_promotion | NumPy 2 里 float32 加 Python float 仍是 float32（NEP 50） | 标准库 json 报"不能序列化" |
| vb_yaml_loader | PyYAML 6 的 `yaml.load` 必须传 Loader | TypeError：缺参数 |
| vb_pydantic_coercion | pydantic 2 不再把数字转成字符串 | ValidationError |
| vb_click_mix_stderr | Click 8.2 去掉了 `CliRunner(mix_stderr=...)` | TypeError：多了参数 |
| ml_renamed_then_alias | 两层故障：模块改名，修好后才暴露 NumPy 1.24 删掉的别名 | 先是找不到模块 |

5 个模板 × 6 个场景 = 30 个案例。它们都不在知识库里，只用来评估，决策树不拿它们训练。和真实项目一样，每个案例都在 requirements.txt 里声明了代码当初针对的版本下限（例如 `numpy>=1.21`）。每个新加的测试都检查函数的返回结果，所以直接删掉出错的代码过不了关。

**结果**（`examples/hard-evaluation/`，决策树用 215 个主案例训练）：

- 加规则前：30 个里对 5 个，只有两层故障那 5 个（D16 确诊）。NumPy repr 被 D40 **确诊**成代码缺陷，其余大多被决策树猜成代码缺陷。
- 加了两条通用的经验规则后，对 15 个。H07 识别"从库里导入的函数拒绝了参数"，负责 PyYAML 和 Click。H08 识别"项目调用的库报错，而且装的版本比声明的下限高一个大版本"。主数据集 215 个案例的结果一个都没变。
- 要诚实说明：**H07、H08 是看过这些难例之后写的**，所以 15/30 是开发结果，不是留出结果。真正的检验要等新的真实项目。
- 仍然判错的有三类：NumPy 的两个场景，证据里看不到 NumPy，一个断言失败在测试代码里，一个报错发生在标准库里；pydantic，它设了 `__tracebackhide__`，把自己的调用帧从 pytest 的 traceback 里藏掉了，FixFirst 看不出报错来自 pydantic，H08 也就不会触发。

**实现要点**：
- 项目检查时静态读取 import 语句（用语法树，不执行），得到"本地名字 → 来源"，例如 `np → numpy`、`CliRunner → click.testing.CliRunner`。TypeError 发生时，FixFirst 用它找出被调用的函数属于哪个包，也就是 H07 的证据。
- H08 用到两个新事实：项目声明的最低版本，以及"项目自己的代码调用了这个库"（traceback 里项目帧出现在库帧之前）。测试框架 pytest 本身不适用 H08。
- 这些新事实都**不进决策树的特征**，所以已经训练好的树不受影响。

**老师可能问**：
- **"规则是不是看着难例写的？"** 是的，所以只报开发结果，并在 `examples/hard-evaluation/before/` 里保留"加规则前"的结果对照。留出检验看新的真实项目。
- **"为什么不直接把这些变化写进知识库？"** 写进去当然能判对，但只对这几个库有效。H07、H08 靠的是通用信号，对知识库没收录的库也适用，这才是泛化能力。

## 11. 已知局限（被问到时诚实说）

1. **合成数据太干净**：单个故障、5 个模板。所以合成数据上的成绩和真实项目差距很大（93% vs 第 1 轮 2/13）。
2. **规则和知识库是团队写的**，写的时候知道场景，生成数据上的规则成绩偏乐观；LOTO 的 100% 不可信。
3. **行为变了但不报明确错误的问题很难**，比如 SQLAlchemy 2.0 改了结果行为、pytest-asyncio 1.0 不再用项目提供的事件循环，FixFirst 会误判成代码缺陷。9/28 加的 H07、H08 能识别其中两种：库函数拒绝了参数，以及项目调用的库在大版本升级后报错。但报错只出现在项目自己的断言里、或者出现在标准库里的，仍然识别不了（见 10.5 节）。
4. **TF-IDF 分组目前没显示出价值**。
5. **试调研 13 个项目的标签只有一个人写**；新的一批由 A 标注、C 独立复核（任务 A1、C1）。
6. **用户研究还在准备**（任务 C2、C3），现在的数字只说明诊断，不说明能帮用户省多少时间。

## 12. 老师可能追问的问题（汇总）

| 问题 | 回答要点 |
|---|---|
| 为什么不直接用大模型诊断？ | FixFirst 在本地运行、不需要云端模型；每一步都有规则、证据和出处，可以追溯；并且只有真实检查通过才算修好。proposal 引用的 Stack Overflow 2025 调查里，66% 的人抱怨 AI 的回答"几乎对但其实错" |
| 44 个特征怎么来的？ | 人工设计，按排查时要问的问题分五组；故意不放解析器分类和标签，防止标签泄漏；树最后只用了 14 个 |
| 决策树会过拟合吗？ | 限深度 6、叶子至少 2 个样本、两种交叉验证、每折重训；没见过的故障类型上单独用树只有 61%，所以只让它兜底 |
| 为什么只用合成数据训练？ | 合成数据答案已知、能均衡、量够；真实项目少、偏，要留着做诚实测试 |
| 标签怎么来的？ | 生成数据：注入的故障就是标签；真实项目：跑 FixFirst 之前人工标注并复核 |
| 规则怎么表示？ | TOML 里的条件 → 结论，条件是带变量的三元组，加上否定和版本比较 |
| 推理引擎怎么实现？ | 自己写的前向链式产生式系统：回溯匹配、分阶段推到不动点、分层否定、每个结论都能溯源 |
| 为什么前向链？ | 从证据出发推出所有结论，属于数据驱动；排错时事先不知道要验证哪个假设 |
| 会不会死循环、规则冲突？ | 不产生新常量所以一定停；阶段顺序加 `not` 条件避免冲突；加载时检查分层和变量绑定 |
| 知识库怎么建、怎么扩展？ | 从官方 release notes 手工整理，每条带出处；新版本加条目即可，不改代码；没收录的由决策树兜底 |
| 怎么判断真的修好了？ | 同一环境、同一范围、真正执行过的检查通过才关闭；部分重跑、跳过的测试、导入的日志都不算 |
| 分组阈值 0.82 怎么定的？ | 事先定、没调参；目前没比完全匹配强，计划用更难的数据改进 |
| 合成数据上 93%，真实项目呢？ | 第 1 轮留出只有 2/13 完全正确，说明合成数据干净得多；所以才要新选 10–15 个真实项目做正式测试 |
| 代码是不是 AI 写的？ | 如实说：用了 AI 编程助手辅助实现，已在 AI 声明里写明；设计取舍、数据方案和评估方法是团队定的，并且每个模块的原理都能讲清楚（就是这份文档的内容） |

```bash
.venv/bin/fixfirst knowledge --output workbench/kg.json
```

把知识图谱和规则导出成 JSON。

```bash
.venv/bin/fixfirst evaluate examples/diagnosis-dataset --output workbench/re-eval
```

用现成的 215 个案例重跑交叉验证，不需要重新执行项目。

```bash
.venv/bin/fixfirst dataset --suite diagnosis --output workbench/diagnosis
```

## 附录 C：术语表

| 中文 | 英文 | 一句话解释 |
|---|---|---|
| 前向链式推理 | forward chaining | 从已知事实出发，不断应用规则推出新事实 |
| 不动点 | fixpoint | 再应用一轮规则也推不出新东西的状态 |
| 否定即失败 | negation as failure | 找不到某个事实，就当它不成立 |
| 分层否定 | stratified negation | 否定只能针对更早阶段就已算完的结论 |
| 溯源 | provenance | 每个结论都记着由哪条规则、哪些事实推出 |
| 产生式系统 | production system | 由"条件 → 动作"规则和推理引擎组成的系统 |
| 基尼不纯度 | Gini impurity | 决策树选分裂点的指标，越小说明一个节点里的类别越"纯" |
| 交叉验证 | cross-validation | 轮流留出一部分数据做测试，其余训练 |
| 留一个场景 / 模板 | LOSO / LOTO | 每次留出一种故障场景 / 一个项目模板做测试 |
| 消融实验 | ablation | 去掉某个组件，看效果掉多少，以此证明它的作用 |
| Macro-F1 | Macro-F1 | 各类分别算 F1 再平均，不让大类掩盖小类 |
| 自助法置信区间 | bootstrap CI | 反复有放回抽样估计结果的波动范围 |
| 标签泄漏 | label leakage | 输入里混进了答案，模型只是在抄答案 |
| 留出测试 | held-out test | 开发时完全没看过的测试数据 |
| TF-IDF | TF-IDF | 按词（这里是字符片段）的重要性把文本变成向量 |
| 余弦相似度 | cosine similarity | 两个向量夹角的余弦，越接近 1 越相似 |
| 完全链接 | complete-link | 一组里任意两个都足够相似才能合并 |
