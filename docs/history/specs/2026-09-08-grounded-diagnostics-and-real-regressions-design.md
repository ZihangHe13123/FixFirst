# 依赖建议与历史故障：三轮优化设计

沿用已经获准持续实现与优化的本地 Python 排查产品范围。本轮按三个可单独验收的增量实施，不修改被排查项目，也不增加服务端和付费模型。

## 取舍

扩充更多相似模板成本低，但不能证明真实项目价值；直接接入整个 BugsInPy 涉及旧 Python 与复杂依赖，复现成本较高。本轮选择少量可固定版本、保留来源的真实第三方库历史回归，配合项目声明分析。它们能检验真实 traceback 和状态闭环，但不能代表完整开源项目或开发者效率。

## 第一轮：建议引用实际项目声明

增加只读 `project` 检查，限量读取项目内 pyproject.toml、requirements 文本和 setup.cfg，不执行 setup.py，不解析任意脚本。记录文件内容哈希、声明来源、解析边界；递归 requirements 必须在项目目录内且有文件与大小上限。

结合目标解释器快照，区分声明依赖缺失、版本不满足、条件依赖未启用、可选依赖、当前 Python 不满足 requires-python。使用标准 requirement / version / marker 解析，不能把宿主机器的环境当目标环境。导入名到发行包名只使用实际安装元数据，不凭名称猜安装命令。检查失败和不支持格式显式保留。

建议必须展示包名、约束、已安装版本及文件来源；相关事实进入现有图谱并能追溯至 Run。旧记录没有新检查时仍可加载，缺少证据时保留通用建议。目标通过继续由测试/代码检查证明，声明检查不替代真实执行。

## 第二轮：真实历史回归闭环

选择 Packaging / Click 官方修复记录中的小型确定性回归。下载固定发行版本 wheel，保留来源 URL、SHA256、许可证和修复链接；在产品自建目录的独立环境执行。每个案例保留故障版本失败与修复版本通过的日志、测试源码和报告。安装只发生在显式启动复现实验后创建的专用环境。

复现程序与断言明确标为根据上游问题编写的最小复现，不冒称直接运行了整个上游测试套件。外部源码与许可证分开保存，不归入原有 CC0 自建数据。失败或无法复现的案例也记录原因，不把安装成功当作复现成功。

## 第三轮：用新证据改进可靠性与可读性

根据复现中观察到的问题修正解析、归并或建议；增加困难输入检查，保护不同包、约束、节点和错误值。重点检查陈旧快照不生成当前结论、未知/可选声明不被当作必修故障、同一测试反复失败不膨胀问题数量。

最后更新面向队友的变化说明、pain point → feature 表、模块分工和可重复验收命令。保留旧示例作为历史记录，发布新版本源码与可分享数据。模型优势、真人节省时间和课程评分不作未经测量的承诺。

## 验收

- 有意义的单元与真实子进程回归；Ruff 全部通过。
- 旧 session 和现有 64 项检查回归兼容；新声明来源能在 HTML 与 KG 查看。
- 历史回归实际完成故障 → 通过，测试源码不随版本切换改变；来源与哈希可复核。
- 新环境安装、CLI、完整示例、桌面/窄屏报告可用；版本、文档与 ZIP 一致。
