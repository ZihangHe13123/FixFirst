# 可选扩展计划：人工验证数据训练与生成数据路线

日期：2026-09-29

状态（2026-09-30 更新）：已开展开发侧的自动复现和探索训练，见[第三轮核心模型对照](../experiments/core_diagnosis/OBSERVATIONS.md)。验证了旧公开项目的 6 个故障及 1 个健康对照，并构造了 15 个训练反例；新的人工收集与复核尚未完成。这批自动验证记录不能称为新人工金标准。增量训练出现误报或迁移退步，未采用其权重。当前 A、C 分工不变。

2026-10-04 补充：新的 v0.8.0rc1 候选已采用固定 81 特征树，见[候选验收](validation/2026-10-04-tree-integration.md)。下文 9/29–9/30 的计划、基线和数字保留为历史记录。

## 1. 定位与启动条件

本计划记录一条有余力时可以增加的路线：**先整理人工验证的真实开发案例，做小规模训练对照，再根据结果决定是否扩充生成数据。**

当前仍按[任务清单](tasks/README.md)、[B 的任务](tasks/B-tasks.md)和[后续计划](后续计划.md)推进。本文不新增任务编号、负责人承诺或截止日期，也不增加 A、C 当前需要交付的数据量。

启动时满足以下条件，并记录实际可用时间和参与者：

- 当前阶段的正式交付能够按期完成；影响冻结、实验有效性或队友开工的问题已优先处理。
- 能划出明确的时间预算，优先完成一个小试，再决定是否扩大。
- 数据来源和用途已分清，开发侧不接触尚未公开的 A1/C1 留出材料。
- 人工核实有实际参与者；工程工作沿用 B 的职责。A、C 如有余力，可以另行认领额外开发数据，本文不自动给他们加任务。

默认把结果保存在独立实验目录和模型文件中。若时间不足，就保留为后续研究计划，继续完成原定交付。

## 2. 要回答的问题

1. 在现有生成数据之外加入人工确认的真实故障，能否改善根因分类？
2. 改善能否传递到 FixFirst 的第一步建议，还是主要受证据特征或建议规则限制？
3. 哪些故障类别和环境值得继续收集，哪些适合随后用大模型辅助扩充？

首轮目标是得到可复现的开发实验结果和错误分析。少量样本上的提高只支持继续探索；样本量、类别覆盖和独立项目数量决定结论能说到什么程度。

| 项目 | 当前基础 | 对本计划的意义 |
|---|---|---|
| 可训练模块 | Gini 决策树，44 项证据特征，5 类根因；当前内置模型记录 215 个训练样本 | 第一轮可以直接研究数据带来的影响 |
| 训练入口 | `src/fixfirst/classification.py` 的 `train_tree`；默认 `max_depth=6`、`min_samples_leaf=2`、随机种子 42 | 首轮保持参数一致 |
| 系统使用方式 | 规则、知识和经验规则优先，决策树负责后备建议 | 同时测树本身和完整系统 |
| 旧真实项目 | 13 个试调研项目，已有原始输出、环境和标签修订记录，并被用来改进系统 | 可作开发材料；先审核标签及修法，不能再作独立新项目测试 |

五类训练标签沿用当前定义：`missing_dependency`、`local_module`、`version_incompatibility`、`config_missing`、`code_defect`。健康项目单独用于检查误报，首轮不新增树的分类类别。

本轮保存根因、修法和验证证据。决策树实际学习的是“证据特征 → 根因类别”；操作记录可供以后研究使用。离线语言模型微调和 agent 行为训练放在后续阶段另行设计。

## 4. 数据分工与隔离

| 数据 | 本计划中的用途 | 使用约定 |
|---|---|---|
| 旧 13 个试调研项目 | 数据适配、训练、错误分析 | 审核修订后的标签；既有系统已经见过这些项目 |
| 新增真实开发案例 | 人工确认后用于训练或开发验证 | 在训练前按项目和故障来源分组，固定用途 |
| 当前生成数据 | 基线训练、混合训练和已有能力的回归检查 | 两组使用同一份快照；冻结时数据量更新后也保持这一点 |
| 30 个难例 | 开发压力检查 | 已用于规则开发，报告中继续写作开发数据 |
| A1/C1 新留出集 | 按 A2 检验正式冻结版本 | 本轮不用于训练、特征设计、规则修改、提示词调整或数据生成 |
| B12、B17 及用户研究材料 | 各自原定实验 | 保持原用途，本计划不自动纳入训练 |

新增开发候选可以先由开发侧准备一份清单，请 A/C 只返回是否与私有留出候选冲突；开发侧不索取私有名单、报错或标签。存在重叠时，替换开发候选，并记录原因。

同一项目、同一修复提交、同一故障的改名版本、以及从它生成的变体应归入同一组。有关联的组应合并后再划分，避免近似案例跨越训练和验证。

已经用于训练或调整系统的案例，此后继续作为开发数据。A2 公开结果后，若据此产生新模型或新规则，需要另找未参与开发的测试集来验证新版本。

## 5. 阶段一：整理人工验证的开发数据

### 5.1 先盘点，再小批补充

1. 审核旧 13 个项目的标签、修法、环境及修订历史，区分已验证、待补证和无法纳入的案例。旧标签不能自动视为经过双人复核的标准答案。
2. 选 3–5 个证据齐全的开发案例跑通数据适配。这一步只检查数据和流程，不据此宣布准确率提高。
3. 如仍有余力，首批可补充约 10–20 个经过验证的独立故障，重点补代码缺陷、配置缺失等薄弱类别，并覆盖不同项目和环境。此数量是可调整的工作量建议，不是效果保证或新增交付要求。
4. 保留少量健康项目作误报对照。若无法形成独立的开发验证项目或某类没有样本，只报告实际覆盖与不足。

旧项目中的版本问题较多，因此不能用它们的平均结果代表所有类别。一个故障触发的多个失败测试需要关联到同一故障，记录真实的项目数、故障数和报错数。

### 5.2 每个案例至少记录什么

| 信息 | 要记录的内容 |
|---|---|
| 身份与来源 | `case_id`、项目 URL、源码提交、故障来源、关联组、许可和分发条件 |
| 原始环境 | OS、Python、依赖版本、安装步骤、执行命令和目标 |
| 失败证据 | 修改前的原始检查输出、重复运行结果、相关测试或 issue 标识 |
| 人工判断 | 根因、对应故障层、判断依据、资料链接、标注人与日期 |
| 修复验证 | 在独立副本中的最小改动、修复前后结果、消失的问题和后续故障层 |
| 建议判分 | 正确的第一步、可接受替代方案、部分正确与错误的边界 |
| AI 辅助与复核 | 助手及版本、使用日期、采用或否定的建议、人工核实与复核记录 |
| 数据用途 | 训练或开发验证、划分版本、排除原因、已发生的开发侧接触 |

人工可以用 AI 理解报错、查找来源和提出验证方案，随后亲自核实来源与修复效果。可参考 [AI 辅助记录模板](tasks/templates/ai-assistance.md)。人负责最终判断，并保留不确定项；不能验证的候选先排除并记录，不为了凑数猜类别。

第一层故障修复后仍有其他失败，可以记录“第一层已解决”和后续层；不能写成整个项目已修好。仅靠增加等待时间后偶尔通过，也不足以认定具体根因，需要重复验证并记录时序或环境因素。

### 5.3 接入训练时的检查

- 使用修复前、正常诊断时能够取得的证据提取特征。标签、标准修法、修复提交内容和人工解释只用于监督与核验。
- 核对每条训练记录对应的具体故障；不能把项目第一层标签直接复制给项目内所有不同根因的报错。
- 首轮优先选择第一层原因清楚、可稳定复现的案例；多故障无法拆清时暂不进入训练。
- 固定每个独立故障的取样办法，避免产生很多报错的项目在训练中占据过大比例。
- 修复和验证都使用案例副本及独立环境，保留原始失败状态和检查范围。

**阶段交付：** 数据说明、候选及排除记录、核实后的标签、原始证据、修复验证、训练/验证分组清单、数据适配说明。

## 6. 阶段二：做一次固定条件的训练对照

### 6.1 两个主要方案

| 方案 | 训练数据 | 用途 |
|---|---|---|
| S：生成数据基线 | 固定快照的现有生成数据 | 作为数据增量实验的参照 |
| S+H：人工真实数据增量 | 与 S 相同的生成数据，加人工确认的真实训练案例 | 观察加入真实案例后的变化 |

可以在数据足够时补做“仅人工真实数据”组，作为探索，不作为首轮必须项。

两组固定特征提取、规则、知识库、树参数、置信度阈值、验证集合与运行条件。若发现需要补特征或规则，先保存本轮结果，再开下一轮实验，明确新增变量。

### 6.2 验证办法

1. **训练前划分。** 新开发数据按项目及关联故障分组，预先保存训练/验证清单。旧 13 个项目默认放训练与调试侧。
2. **优先验证独立项目。** 两组都在相同的开发验证案例上预测。若样本只能支持分组交叉验证，明确每折的项目及训练数据，并在每折重新训练；不足以覆盖的类别报告样本不足。
3. **防止旧经验混入结论。** 旧项目即使被交叉验证留出，固定规则仍可能已针对这些开发材料改进；这种结果标为开发分析。
4. **控制迭代。** 看开发验证结果后可以继续改进，所有轮次保留。反复使用的开发验证集不能承担最终独立评测。
5. **正式留出继续按原协议。** A1/C1 数据由 A2 使用，本试验不额外索取或反复运行这批数据。

### 6.3 记录哪些结果

- 树本身：Accuracy、Macro-F1、各类别 precision/recall/F1、混淆矩阵、项目数与故障数。
- 后备建议：在规则和经验规则未覆盖的相同案例上，记录树的正确率、输出建议的比例和错误建议数量。
- 完整系统：根因是否正确、第一步是否可执行且正确、健康项目是否出现误报。
- 运行代价：训练时间、模型文件大小、相同条件下的诊断耗时。
- 已有能力：固定生成数据和难例开发集上哪些结果改变。训练集上的结果用于回归检查，另列泛化验证结果。

小样本同时给出正确/总数、逐案例变化和类别样本数。需要区间估计时按独立项目或故障组计算；独立组太少时明确不确定性，避免把重复报错当成额外样本。

第一步建议由人按已固定的标准判断，标准修法不能替代系统自己给出的行动。没有完成实际验证时，区分“人工判为合理”与“执行后解决故障”。

**阶段交付：** 代码提交号、数据与划分快照、两组模型、参数、逐例预测、指标表、错误分析和可复现步骤。目录中的运行结果使用唯一编号，保留失败及无改善的轮次。

## 7. 根据结果决定是否扩展

| 观察结果 | 下一步 |
|---|---|
| 加入真实案例后，在多个独立项目上出现一致改善，关键类别和误报未明显恶化 | 扩大人工数据，并围绕缺口准备生成案例 |
| 仅训练数据变好，开发验证没有改善 | 检查重复案例、标签质量、类别偏斜和过拟合 |
| 不同根因在现有特征下无法区分 | 下一轮先补可观察证据，再重做受控比较 |
| 根因分类改善，第一步建议仍不正确 | 检查建议规则或研究案例检索，记录为新的改动因素 |
| 结果依赖少数项目、类别覆盖不足或复现不稳定 | 补充验证；结论保持“尚不能判断” |
| 原定任务开始受影响 | 停在已完成阶段，归档开发结果，优先正式交付 |

启动首轮时，根据样本数量预先写下继续扩展的判断标准；不在看到结果后只挑有利指标。小试得到“目前没有可靠提升”同样是有效结果。

## 8. 阶段三及以后：生成数据、检索与小模型

仅在人工流程和验证办法可用、并且还有余力时考虑以下路线。

### 8.1 大模型辅助生成数据

让教师模型针对已明确的开发缺口提出故障场景、候选根因、修法和验证步骤。记录模型、提示词、参数和版本；在独立环境中执行，检查故障是否真实出现、修法是否解决指定问题，过滤失败、重复和原因不清的案例，并记录过滤数量。

生成前先固定数据所属组，变体沿用原始项目及故障的分组。保留一批人工复核记录，并报告抽查数量和发现的问题。仅有文字解释、无法运行验证的候选，不能直接当成已验证训练案例。

再比较“生成数据基线”“加入人工真实案例”“再加入教师辅助生成案例”，复用同一开发验证口径。大模型生成了多少条记录和系统实际改善多少分开报告。

### 8.2 后续可选方向

| 路线 | 需要补的工作 |
|---|---|
| 继续改善规则与决策树 | 补足证据、可靠标签和类别覆盖，逐轮分清数据与算法贡献 |
| 离线案例检索 | 把已验证案例整理成可查的证据与修法，评估检索是否适用、建议是否正确 |
| 离线语言模型微调或蒸馏 | 准备适配模型的训练记录、训练资源和独立评测，研究诊断与修复建议的迁移 |
| agent 行为训练 | 另行定义状态、动作、执行反馈和完整轨迹，制定任务级判分与训练方案 |

本计划不预先承诺上述路线都要完成，也不指定付费教师模型或启动服务。数据规模、验证成本、模型能力和时间预算确定后再选择。

## 9. 与冻结和课程交付的关系

- 当前分工、Issue、截止日期及 B5 冻结安排继续有效。本文保存可选扩展，不代表新实验已经完成或列入必交项。
- 小试模型使用单独文件和实验记录，默认不替换正式内置模型，也不改变现有 B3/B6/B7 等实验的条件。
- 如果冻结前决定纳入正式版本，需要明确更新冻结范围、模型与数据快照，并在接触留出结果之前锁定待评测系统。比较范围有变化时同步记录，保留原方案作为参照。
- 冻结后开展的改进作为附加开发实验或后续版本，不能用改进后的成绩覆盖原冻结版结果。
- 尚未执行的内容在报告中写为计划；开发验证、正式留出结果和用户研究分别报告。

- 结果：增加真实数据未改善逐项目留出的树结果，并引入普通校验误报；增加生成反例改善误报但损失难例迁移。两类增量权重未采用。当前候选只训练配对生成观察。
- 后续：先补齐类别覆盖和人工复核，单独执行系统自己输出的第一步，再判断数据增量的收益。参考修法已验证不代表系统第一步已验证。

逐例结果、未通过的尝试、候选模型、源码与输入哈希见[第三轮报告](../experiments/core_diagnosis/OBSERVATIONS.md)及其数据目录。
