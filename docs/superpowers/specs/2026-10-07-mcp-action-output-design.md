# MCP 动作优先输出与 YAML 调用提示

## 已确认的目标

方案 v1.11 的 P3、P4：MCP 每一步先给可执行动作，动作不被说明文字的截断丢掉；确定为代码缺陷时说明改环境不能解决，移除与当前目标无关的附带发现。P5 保持现有明确重试提示。

基线为 `9a7e956ec0610f0ffb29d992d47b40482a6da649`。运行器、H5、模型和开发结果不改。只使用公开开发包与已有验收材料。封存评估包在产品冻结后再交付。

## 实现取舍

采用明确分开动作和说明的结构：动作有自己的文本，命令和动作先输出，解释仍可限长。这样不会靠正则猜哪一句是修法，也不会因长替换写法被截断而丢失修改要求。

另两种方式的取舍：把整段解释前移并全部输出，改动小但会把大量限定说明重新塞进每次回复；批量改写知识条目，容易影响已验证的替换语义和来源。以上两种不作为本轮的主方案。

## P3：保留动作

1. 为计划动作增加可选的明确操作文本，旧会话缺这个字段仍可加载。规则、现有精确迁移与配置建议可以提供它；没有明确修改办法的步骤保持审查建议。
2. MCP 步骤顺序：标题、完整 Command 或 Action、必要的文件位置，然后 Cause、Why、Confirm。可执行内容不使用解释的 600 字符限长。
3. 为知识支持的替换步骤提供完整替换内容。一个修法里的条件与语义限制跟随动作一起保留；不能把“标准数据”等适用条件切掉。
4. 旧动作没有操作文本且没有命令时，保留完整原文，避免丢掉已有的修法。`explain` 仍可返回完整说明和来源。
5. 修复不自动执行；命令的解释器、范围、版本约束和安装反馈机制保持原样。

## P4：准确说明边界

- 只有规则确认的代码缺陷显示“这是项目代码或测试的问题，改环境不能解决”；树的猜测和启发式诊断仍保留不确定措辞。
- diagnose/check_again 不再列出不影响当前目标的 Other findings。explain 可以继续展示细节，网页版与 CLI 的其他目标检查不因此改变。
- 不新增“全部通过”的推断，确认仍依赖原始完整检查与基线。

## d1 的补充修复方案

公开开发题 d1 的第二层是 PyYAML 6 的 `yaml.load(text)` / `yaml.load_all(text)` 缺少 Loader。声明本来要求 PyYAML>=6，原来的行为变化规则只在旧版本兼容背景下给迁移建议；这里应保留代码调用错误的分类。

建议增加有明确归属和版本条件的调用指导：

- 实际调用归属于 PyYAML，失败位置和调用对象一致，缺少的必填参数恰为 Loader，且库版本适用，才给该建议。
- 单文档标准 YAML 用 `yaml.safe_load`；多文档标准 YAML 用 `yaml.safe_load_all`。保留调用参数、别名、周围类型检查和生成器消费方式；需要自定义标签的应用明确要求复核其构造器，不声称替换必然等价。
- 不把现代合同错误改判成版本冲突，不建议降级，不覆盖项目自己的同名 load/load_all、被遮蔽导入、重新抛出的异常或没有调用归属的旧记录。
- 按已有精确指导的方式取代同一问题的泛泛步骤，不使用任务名字或测试预期选修法。

用户已在本对话确认“同批补 d1 的具名修法”，与 P3/P4 一起交付。
