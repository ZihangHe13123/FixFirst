# Agent 运行条件修订

## 依据与范围

用户要求继续推进，并转交了六次开发复验的离线复核。先修运行条件，再评估工具收益；业务算法定位暂缓。旧 78 行、六次复验、B3 和冻结版本保持原记录。

原始六行确认：五次失败均未耗尽 20 轮 / 900 秒；11 份截断响应占输出 token 的 45056/83161（54.2%）。这是停止机制和成本的证据，不能证明它们解释了全部失败。两个任务仍能描述其条件下的结果，但不足以估计 FixFirst 的一般收益。

## 选择

直接扩大整个实验会混入运行条件和任务变化。只改产品会保留当前运行器缺口。采用有独立提交的运行器修订，先以假响应和临时文件验证；下一批模型运行另行冻结。

## 行为

1. `--file-read-mode paged`：`read_file` 接受零起点字符 `offset` 和 `limit`（1–6000），从文件头开始，返回正文、总字符数、下一偏移量和结束标志。分页不能漏字符，包括超长单行和 Unicode。保留 `tail` 模式以重放旧接口；同一批三组使用同一模式。
2. `--max-no-tool-reminders 1`：仅完整、非空、明确 `stop` 且没有工具调用的响应可收到一次共同提醒。每次运行最多一次，计入原轮数和时间预算。第二次无工具响应正常结束。空回复、未知结束原因、拒绝、超时、网络错误和截断工具调用不会获此重试。
3. 显式 `--top-p`、`--top-k` 参数传给服务并记入设置。缺省不覆盖服务参数；无效值在创建运行目录前拒绝。`max_tokens`、temperature 已有开关，无需增加机制。
4. 分页模式、提醒额度、显式采样参数全部进入协议身份。历史行没有这些字段时，原协议号不变。
5. 完整响应仍须在工具执行前落盘；不改变沙箱、判分、测试保护和参考修复。

## 下一批登记条件

Qwen 官方卡建议思考模式的精确代码任务使用 temperature=0.6、top_p=0.95、top_k=20，多数查询输出上限 32768。以此作为下一批候选条件，保持 20 轮 / 900 秒，不声称调参必然增加成功率。服务是否实际采用参数、聊天模板和默认 min_p/惩罚项须在登记时核实；不能仅凭请求字段宣称生效。

先冻结开发任务候选池：依赖缺失/冲突、已移除接口、导入路径等诊断瓶颈，参考修复不改测试、不削弱选测配置。只按事前规则考察 baseline 是否有可测余量，禁止看 facts/mcp 成功率后挑题。Django/slugify 可留作运行器回归，不作为主要工具收益样本。新留出数据另行隔离。

## 验收

假响应验证提醒次数、原时间/轮数上限、结束原因、截断调用不执行和响应先落盘；临时文件验证分页完整重组、长行、Unicode、越界、无效参数、链接/特殊文件边界；抓取 HTTP 请求验证采样参数；重算旧 78 行和六行协议与汇总。此轮不启动真实模型。
