## 目的

两次都通过、原来的测试确实都运行且未改动，才允许关闭。未通过的第一次检查仍沿用原来的诊断流程。

## 方案取舍

| 做法 | 取舍 |
| --- | --- |
| **补一次带项目选项的确认（推荐）** | 保留现有采集能力，能分别说明原检查和项目配置的结果；多跑一次测试 |
| 首次就完全使用项目选项 | 少跑一次，但缺插件、选测和输出选项会阻断原来的诊断，影响已有报告 |
| 继续要求用户自己运行 | 最小改动，但没有交付 G 要求的自动确认 |

## 何时补跑

仅用于 `pass_tests`，CLI、MCP、Web 和 Python 接口走同一条流程；默认发现与保存的测试范围都适用，不新增公开参数。

首次运行必须是实际执行、完整记录、至少一条真正通过的测试、退出码 0，且测试/判分设置仍与基线可比。记录不全、导入的旧日志、跳过或 xfail、测试被改空、测试设置被改过，都不能借 G 变成修好。

没有项目选项、或只有现有算法认定等价的显示选项时，不补跑、不改报告。外部 `PYTEST_ADDOPTS` 若含非显示选项，不自动执行它，也不宣称确认了原命令；仍要求用户自行核对。

## 从哪里读选项

使用首次运行中 pytest 实际选中的配置文件和已经观察到的原始 `addopts`，不把多个文件合并，也不猜优先级。来源包括 `pytest.ini`、`.pytest.ini`、`tox.ini` 的 `[pytest]`，`setup.cfg` 的 `[tool:pytest]`，`pyproject.toml` 的 pytest 表，以及目标 pytest 支持时的 `pytest.toml`、`.pytest.toml`。

配置的选择和解释交给同一个目标 pytest。主进程只接受有界的字符串/字符串数组，记录文件路径与内容摘要，确认它是项目内可读取的普通文件、前后内容相同。无法读懂、超限、路径在项目外或文件变化时，不补跑，不关闭，并说明配置无法确认。

第二次仍由同一个解释器执行 `-m pytest`，相同工作目录、保存的范围/局部目标、记录插件和现有进程限制；去掉产品清空 `addopts` 的覆盖，让同一份配置生效。没有 shell，不运行 Makefile、tox 命令或配置里的其他命令，也不自动安装插件或修改项目。

## 选项的边界

1. `-k`、`-m`、`--ignore`、`--deselect`、上次失败筛选等选项可以由 pytest 正常处理，但第二次实际节点集合必须与第一次相同；缺一条就不关闭。`-x`、`--maxfail` 提前停止也不构成完整通过。
2. 需要额外插件的选项照常交给 pytest；插件缺失或选项未知时记录启动失败，不能把未启动说成通过。
3. `--collect-only`、`--setup-only`、帮助/版本/调试交互模式，以及更换配置、根目录、覆盖 `addopts`、禁用/替换记录插件的选项，不自动采用；明确说明它们改变运行或妨碍观察，保持待核对。不能偷偷删掉这些选项再宣称用了项目配置。
4. 其余 pytest/插件选项原样交给 pytest 解析，包括警告当错误、严格 xfail 等判分选项。它们改变结果时，记录真实失败，不降低判分条件。
5. 并行分配测试的选项（如 xdist 的 `-n`、`--dist`、`--tx`，以及 `--workers`）不自动采用；尚未证明多进程共享逐条记录的完整性。即便设置成零个 worker，也按这条保守边界处理。

## 结果怎么保存与判定

两次运行各自保存命令、范围、原始输出、逐节点记录和完成记录。第二次标为项目配置确认，绑定首次 `run_id`、配置摘要、环境身份和首次节点集合。已有 `Run.pytest_options` 字典可容纳这些附加证据，无需改变 MCP 工具定义。

确认成功必须同时满足：

- 第二次实际执行正常结束，退出码 0；逐节点的 setup/call/teardown 和完成记录完整，未丢记录；
- 两次的规范化节点集合相同，原问题对应节点都真正通过；skip、xfail 和非严格 xpass 不替代通过；
- 解释器、检查范围和配置绑定相同，检查前后测试与设置仍通过现有完整性检查。

只要确认没有成功，这一轮就不能从第一次的通过自动关闭。第二次的真实失败仍可诊断；原问题保持未解决或等待核对，并说明是哪项证据缺了。旧记录不补造确认结果。

选择严格相同的节点集合：项目选项新增测试时，即使全部通过也不关闭，备注明确写出新增数量；不默认为这些额外测试建立新的基线。

G 另绑定项目 pytest 配置的完整选项集合与文件集合，保留精确的选项名，只排除允许修复的 `pythonpath`、`DJANGO_SETTINGS_MODULE`。这样未列在旧完整性清单里的未来选项也不能被关闭或新文件遮盖后冒充原测试。配置的字节摘要在本轮第一次运行之前、插件启动时、第二次运行前后都要一致。旧会话若缺这层基线，不补造历史证据，只提示建立新的基线。

第二次按项目配置运行，可能写出覆盖率数据或测试报告；文档与记录注明这一点。完整性检查仍只比较测试 Python 文件与测试设置，普通 `.coverage`、XML/HTML 报告不会成为新测试。输出若真的覆盖了测试或配置文件，仍拒绝确认。

第二次调用同一个采集函数，因此沿用 A 的旧版本参数、B 的节点归一化和 C 的独立失败记录预算。无完整记录就不确认。

## 用户会看到什么

| 第二次的情况 | 结果与说明 |
| --- | --- |
| 同一批测试完整通过 | 确认修好，备注已带项目 pytest 选项核对 |
| 测试失败，例如警告升级为错误 | 不关闭，说明带项目选项后仍失败，保留真实失败 |
| 选项排除了原测试 | 不关闭，说明原节点没有全部运行 |
| 缺插件、未知选项、内部错误 | 不关闭，说明项目配置确认未启动或中断，保留输出 |
| 超时、取消、记录不全 | 不关闭，说明确认不完整 |
| 测试或设置被改动 | 沿用“测试被改过/不可比”的说明，不能用通过掩盖 |

同一次 pytest 检查的剩余超时预算供补跑使用；用完则不再启动确认。每次扫描最多补一次，失败不循环重试。
