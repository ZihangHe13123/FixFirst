# 第七轮：安装失败反馈与可执行修复

用户已批准上一条回复提出的方案：安装失败纳入会话、识别真实阻塞、给出可执行新方案，并先用 C1 的原始起点验收。沿用 Codex 实现、Claude 独立验收。生产基线 `5d661e6` 保留；本轮基于第六轮证据完整的分支继续，PR 分开且不自动合并。

## 选择与边界

三条路线：仅补错误文案（不能解决重复安装）；增加自动安装到用户环境（改变原产品执行边界）；**采用建议命令记录日志、扫描反馈、显式构建和隔离试验**。本轮自动检查不安装进目标环境，不自动执行源码构建。所有安装/构建仍是用户明确执行的命令，扫描只接收证据。决策树权重不变。

## 设计

1. **安装反馈**：为生成的 pip install/wheel 命令加入会话和解释器独立的 `--log` 文件。扫描时读取新增的、属于本会话的普通文件，限制大小、拒绝管道/符号链接、避免重复导入。pip 追加日志按最后一次调用切分。日志一律为 imported、退出码未知，不能验证修复；依赖/解释器/声明上下文过期时不继续采用旧失败。记录失败后移除已失败的相同安装建议，优先展示下一步。
2. **失败分类**：保留包名和当前声明，读取构建段中的具体原因。缺 pg_config、编译器或头文件与版本约束、无可用发行版分别处理。未固定的 requirement 不称为固定版本。证据不足不推断全部版本不兼容。
3. **源码包路线**：wheel-only 请求没有匹配发行版时，可提出一个具体声明的 pip wheel 命令，写入本会话的 wheelhouse。源码构建只由用户手动启动，命令解释明确这一点；构建失败的日志也回到会话。临时依赖试验仍只安装 wheel，但允许复制本会话明确请求且名称/版本/元数据一致的普通 wheel 文件。内容指纹参与试验缓存，其他包或来源不明的 wheel 不使用。构建失败后不能重复同一构建步骤。
4. **试验和建议一致**：临时环境和最终安装命令使用同一组准备好的 wheel；复制后的文件用于试验，记录哈希。成功仅证明安装和元数据一致，仍须执行原程序/测试。原声明不自动修改；试验结果给出确切改法。
5. **测试工具与声明差异**：目标所需 pytest/ruff 明确缺失时也能生成安装必需声明的计划。只在当前目标被阻塞时出现，健康项目不新增阻塞。对已安装 psycopg2-binary、声明仍为 psycopg2 的有证据差异给出明确提示和声明位置，不悄悄当成同一发行包。

## 验收

- 先在旧版本保存失败，再在新版本使用相同输入。自动测试覆盖反馈的一次性读取、旧日志、解释器切换、追加日志、截断/管道/符号链接、无失败日志不能报修好。
- 真实本地 sdist/wheel 正反例验证手动构建产物的使用、元数据不符和轮换后缓存失效；安装检查不能冒充项目检查。
- Claude 预先固定验收例：C1 失败不原样重复、源码包限制不冒充版本问题、pg_config、缺 pytest、替代发行包差异。
- 最终生产提交固定后，在 C1 的原 commit/解释器/初始依赖状态的新副本中逐步照做，10 轮/60 分钟，M1/M2/H 分开。目标是无需操作者另想修法；若失败，保留失败与具体阻碍。
- A–G 中原已通过部分不得退化；主套件、相关集成检查按具体改动验证。第七轮没有使用 A1/C1 私有留出、BugsInPy、正式冻结或付费模型。
