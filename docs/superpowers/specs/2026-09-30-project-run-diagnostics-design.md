# 普通 Python 项目的运行、诊断与修复验证

日期：2026-09-30

## 用户确认的目标

FixFirst 的主要用途是检查真实报错，给出有依据的根因和下一步修复建议。普通课程作业不应先安装 pytest、编写测试才能使用它。没有测试时，执行用户指定的程序，修复后以同一方式重新执行，正常结束即完成本次运行目标；有测试时，使用项目已有测试进行检查。

“程序运行完成”表示本次入口和输入执行成功；“测试通过”表示实际测试通过。界面分别表达这两种结果，不把运行成功扩大为业务答案正确。

## 当前实现与改动边界

当前基线为 `11bbe7e`。`models.py` 的目标、`runner.py` 的检查、`evidence.py` 的可诊断来源、规则中的目标关联，以及工作区状态均围绕 pytest / Ruff。仅增加一个执行按钮，不能让脚本报错得到现有根因分析或可靠的修复验证。

本次在现有本地执行、会话存储、规则和报告体系内扩展；保留现有 pytest 会话及回归行为。FixFirst 给出建议，由用户修改程序，再执行 Check again。

## 方案选择

| 方案 | 优点 | 代价与限制 |
| --- | --- | --- |
| 原生运行适配器接入现有诊断和验证流程（采用） | 脚本无需测试依赖；能保留真实运行方式；修复后能重跑 | 需要同时扩展执行、证据、规则、会话和界面 |
| 生成 pytest 包装器后统一运行 | 可以复用部分测试协议 | 仍增加 pytest 门槛，并且容易改变入口、输入和异常语义，不符合本次目标 |
| 只导入用户粘贴的报错 | 改动小，能先分析历史错误 | 无法可靠确认解释器和执行范围，也不能通过重跑验证修复，只作为补充 |

## 用户流程

1. 选择项目目录；直接显示 Python 解释器路径、来源和修改入口。
2. 静态检查目录和配置，显示建议的检查方式及依据。识别过程不导入或执行项目代码。
3. 发现实际测试文件时，建议测试模式；没有测试时，建议运行程序。只有 pytest 配置文件、空 tests 目录或已安装 pytest，不足以证明项目有测试。
4. 运行程序模式允许选择 `.py`、Python 模块（`python -m package`）或 `.ipynb`，并配置参数及脚本标准输入。优先显示明显入口；多个候选时由用户选择，不依次执行目录中所有文件。
5. 点击检查后，收集环境与项目声明，执行选定入口或测试，展示错误位置、原始异常、根因依据和下一步修复建议。
6. 用户修改后点击 Check again，以同一配置重新执行，报告已修复的问题和新出现的问题。

用户可以改选运行程序或测试模式。配置改变后需要重新检查，旧成功状态不沿用。

## 执行方式

### 普通脚本与模块

- 使用选择的 Python，在项目目录执行指定 `.py` 或 `-m` 模块。
- 参数以参数列表传给子进程；UI 提供逐项参数输入，避免 shell 解析在 Windows 和 macOS 上产生不同含义。
- 脚本标准输入可选，用于普通 `input()` 作业；无输入时按结束输入处理，不无限等待。
- 复用现有进程管理、超时、取消、输出上限、环境激活和脱敏机制。
- 交互式终端、持续运行的 Web 服务、GUI 人工操作不以“持续存活”作为成功。超时或中断显示未完成及对应原因。

### Notebook

- 使用标准 Notebook 执行协议，在选择的解释器对应内核中，从干净内核按单元格顺序执行。
- FixFirst 的 Notebook 执行依赖作为可选功能提供；目标解释器需要 `ipykernel`，不需要 pytest。缺少所需组件时明确列出缺项与安装命令。
- 首个失败单元格给出单元格位置、异常与 traceback，接入相同根因分析。
- 执行结果记录在会话中，原始 Notebook 不覆盖。标准输入交互不可用时明确报告，不静默跳过单元格。

### 已有测试

- pytest 项目继续使用现有 pytest 结构化探针和逐测试验证。
- 纯标准库 unittest 项目提供原生 unittest 执行方式，不为它强制安装 pytest。混合或依赖 pytest 特性的项目使用 pytest。
- 自动识别只是建议；支持手动选择测试方式，保留既有显式 pytest 配置行为。
- 未发现测试时显示“未发现测试”，并引导选择运行入口；不将其描述为业务代码错误或测试通过。

## 证据、根因与建议

- 新的运行记录保存执行方式、入口、参数、工作目录、解释器、退出状态和输出；Notebook 另保存失败单元格信息，unittest 保存逐测试结果。
- 原生 Python traceback 解析保留异常类型、消息、项目源文件与行号。异常链保留上下文，优先解释最终未处理异常。
- 扩展 `evidence.py` 的来源过滤，使脚本和 Notebook 的真实异常也进入环境、声明、代码位置和知识规则推理。
- 复用缺依赖、版本不兼容、模块路径、循环导入、缺配置等规则；普通程序异常使用运行相关的修复与重跑文案。
- 已知错误给出具体检查位置和建议；证据不足时保留不确定性及原始输出，不伪造根因。
- 为新的运行模式默认使用规则和已观测证据；现有仅以测试案例训练的分类器不直接当作新运行模式已验证的模型。
- pip / Ruff 是否可执行单独判断。普通运行不因为缺少 pytest、pip 或 Ruff 而被阻止；缺失的辅助工具不冒充程序故障。

## 修复验证

- 普通运行须真实启动、完整结束、退出码为 0，且没有执行器记录的未处理异常，才能标为“程序运行完成”。
- 比较范围包含解释器、执行方式、入口、参数、工作目录和输入标识。更换入口或输入，不会把旧入口的问题标成已修复；输入正文不出现在公开报告中。
- 源文件内容允许改变，因为这正是修复；删除入口、取消、超时、输出截断和历史日志均不能证明修复成功。
- 第一个错误修复后暴露第二个错误时，继续诊断新错误；只有同范围运行成功，才确认该范围的运行问题已修复。
- 测试继续要求真实测试结果；零测试、全跳过或不完整运行不算通过。

## 接口与兼容性

- Web 首页、工作区、CLI 和 MCP 共用相同运行配置、模式选择及会话服务。
- 新增普通运行目标及对应检查类型；旧会话字段有兼容默认值，旧 pytest 会话仍按原目标运行。
- CLI 支持显式脚本 / 模块 / Notebook 配置和运行参数；MCP 通过结构化参数提供相同能力。
- 公共导出继续脱敏，并清楚展示实际执行范围与结论。
- README 更新为普通作业和已有测试两条使用路径，解释依赖、运行结果与验证边界。

## 验收证据

1. 一个没有 pytest、没有测试文件的独立虚拟环境：脚本真实失败，产生具体根因和修复建议；修改后重跑成功，原问题得到验证。
2. 覆盖缺第三方依赖、缺数据/配置文件、语法错误、未定义变量和普通运行异常；错误位置与源文件一致。
3. 带空格/中文的路径、脚本参数、`input()` 和 `python -m` 均使用相同解释器与工作目录正确执行。
4. 改入口、改参数、换解释器、删除入口、超时和取消不会错误关闭原问题。
5. Notebook 真实执行失败并定位单元格，修改后成功；原文件不被覆盖；缺内核依赖有明确提示。
6. 纯 unittest 项目在没有 pytest 的环境运行并完成失败到修复验证；现有 pytest 的逐测试验证回归通过。
7. 无测试项目不会被要求安装 pytest；配置与入口有歧义时要求选择；自动检测不会执行项目代码。
8. Web、CLI、MCP 和保存后重载保持一致；现有测试套件与 Ruff 检查通过，并进行浏览器实际操作验证。
