# FixFirst v0.4：给队友的说明

v0.3 能跑，但三项课程技术里有两项站不住：决策树的特征就是 parser 已经算好的类别（标签泄漏，F1=1.0 没有意义），"前向推理"只有单跳规则、行动其实是写死的 if/else，知识图谱只是一次排查的溯源记录。v0.4 围绕一个真实问题把三项技术重新组织起来：**同一个异常可能有完全不同的根因，要先判断根因才能给对建议**。

## 这一版改了什么

| v0.3 的问题 | v0.4 的做法 | 代码 |
|---|---|---|
| 决策树特征 = 类别 one-hot，学的是恒等映射 | 新任务：预测**根因**（缺第三方包 / 本地模块问题 / 版本不兼容 / 缺配置 / 代码缺陷）。44 个特征全部来自原始证据：真实异常类型、抛出位置（项目 / 测试 / 第三方 / 标准库）、模块是否已装 / 是否标准库 / 是否本地文件 / 是否有相似文件 / 是否已声明、报错文本线索。不读 parser 类别，不读标签 | `evidence.py`、`classification.py` |
| 18 条单跳规则，行动写死在 Python 里 | 产生式规则引擎：变量绑定、分层否定（加载时校验）、版本比较、每个结论都记录规则和输入。67 条规则放在 `rules.toml`，分五个阶段：推导 → 诊断 → 经验判断 → 模型后备 → 行动 | `engine.py`、`knowledge/rules.toml` |
| 知识图谱只有溯源，没有领域知识 | 领域知识库：117 个已移除的模块、API、参数（带移除版本、替代写法、官方来源链接），42 个导入名到包名的映射，异常类型到候选原因。**规则会查询它**；会话图谱新增 Cause、Rule、Source 节点，问答支持中英文 | `domain.py`、`knowledge/domain.toml`、`knowledge_graph.py` |
| 数据：60 个几乎同模板的案例，测试集 7 条 | 新数据集：5 种项目结构 × 43 种故障，共 215 个**真实执行**的案例，0 个被拒绝。部分故障知识库有意没收录，还有几组容易混淆的对照 | `diagnosis_cases.py` |
| 评估：规则和树都是 1.0 | 两种交叉验证 + 基线 + 消融 + bootstrap 置信区间 | `evaluation.py` |
| 界面全中文，只有终端菜单和只读报告 | 全英文；本地 Web 界面，可以运行检查、标记已修改、提问；练习场演示 | `web.py`、`templates/`、`playground.py` |
| — | 修了三个真实 bug：项目里有 `random.py` 时环境快照会崩；完整运行后旧的收集错误关不掉；pytest 打印 `os.environ` 导致环境变量（可能含密钥）被记录 | `runner.py`、`service.py` |

## 实验结果（写报告、做 pre 用）

详见 `examples/diagnosis-evaluation/REPORT.md`。**主讲"没见过的故障类型"这一列**，它最接近真实使用场景：

| 方法 | 没见过的故障类型 | 没见过的项目结构 |
|---|---|---|
| 只看 parser 类别（v0.3 基线） | 41.9% | 41.9% |
| 规则，不用知识库 | 48.8% | 48.8% |
| 规则 + 知识库 | 79.1%（答了就 100% 对） | 79.1% |
| 只用决策树 | 60.9% | 95.8% |
| **规则 + 知识库 + 决策树后备** | **93.0%** | 100% |

三句话讲清楚每项技术的贡献：

1. **知识库**：有它，规则在它覆盖的故障上准确率 100%；去掉它，规则只剩 7%，混合方法只剩 64%。
2. **决策树**：在知识库没覆盖的故障上，把准确率从 69% 提到 90%。
3. **规则**：只在有依据时才回答，回答就一定对，并且每条建议都能追溯到证据和官方文档。

**不要讲**"没见过的项目结构 100%"。那一列所有故障类型在训练里都见过，数字好看但说明不了什么，老师一看就会质疑。

## 真实项目测试（报告里很有分量）

详见 `docs/REAL_PROJECTS.md`，用 `scripts/setup_real_projects.sh` 可以重现。三个真实开源项目：

- **humanize**（依赖齐全）：正确判断为"所有测试通过"。
- **humanize（缺测试依赖）**：正确指出"安装项目声明的 freezegun"。
- **Flask 1.1.4 + 今天的库**：一开始一个测试都跑不起来。照着 FixFirst 的建议走了 5 轮（jinja2 → markupsafe → itsdangerous → werkzeug → pytest），最后 **524 个测试通过**。剩下 2 个失败超出了它能拿到的证据，文档里如实写明了原因。

这次测试还暴露并修复了 7 个合成数据里没有的问题，比如 conftest 加载失败被当成"不阻碍目标"。这说明合成数据集的局限，也说明拿真实项目验证是必要的。被问到"真实项目上效果怎样"时，就讲这个案例。

## 答辩可能被问到的问题

1. **"决策树用什么特征？"** 44 个从原始证据提取的特征，列表在 `evidence.FEATURE_NAMES`，最终那棵树可以直接打开 `decision_tree.txt` 看。特征里没有 parser 的类别，也没有标签。
2. **"规则是你们自己写的，数据也是你们自己造的，不是循环吗？"** 是的，所以要看"知识库没覆盖"那一栏和"没见过的故障类型"那个协议，报告里也明确写了规则分数偏乐观。决策树每一折都重新训练，而且不包含被留出的那一组。
3. **"为什么不直接用 ChatGPT？"** FixFirst 在本地运行；每条结论都能追溯到检查记录和官方 release notes；知识库没有依据时，只把模型的判断作为"待确认线索"，排在有证据的建议后面，不会编造。
4. **"真实项目上效果怎样？"** 讲 Flask 1.1.4 的案例：5 轮建议，从零到 524 个测试通过；剩下的 2 个失败说明了它的边界。用户研究还没做，这是接下来的重点。
5. **"失败案例呢？"** 报告最后一节列了：普通字典的 KeyError 被判成缺配置、有 bug 的 fixture、被整个移除的库子模块。

## 每个人要读懂的部分

纯靠 AI 写的代码最大的风险，是答辩和个人反思时说不清楚。每人至少读懂自己这一块，能在白板上讲出一个例子：

| 负责人 | 必须读懂 | 能讲清楚的例子 |
|---|---|---|
| A：数据与证据 | `evidence.py`、`diagnosis_cases.py`、`runner.py`、`probe.py` | 一个 `KeyError` 是怎么被判断为"os.environ 查找"的；数据集的一个案例是怎么生成的 |
| B：推理与模型 | `engine.py`、`rules.toml`、`reasoning.py`、`classification.py`、`evaluation.py` | 规则 D02 怎样匹配 `numpy.float`；为什么否定条件要分层；两种交叉验证有什么区别 |
| C：知识与界面 | `domain.toml`、`domain.py`、`knowledge_graph.py`、`web.py`、`report.py` | 一个建议是怎么追溯到 Python 官方文档的；Web 界面怎样防止其他网页调用它 |

## pre 现场演示（约 2 分钟）

1. 运行 `.venv/bin/fixfirst serve`，在首页点 **Open a sample project**。
2. 讲解：页面顶部一句话说明现状（"2 problems to fix"）；下面按顺序列出要做的事，每一步都写明**改哪个文件第几行**（比如 `pricing.py:1`）、根因和改法。可以展开第 1 步的 "Details"，展示判断它的规则和 Python 官方文档链接。
3. 按 `FIXES.md` 改两行代码，点 **Check again**：这两个问题进入 "Fixed and verified"，同时出现两个之前被挡住的运行期错误。强调一点：只有真实检查通过才算修好。
4. 改完剩下两处，再点 **Check again**，页面显示 "✓ All tests pass"。
5. 如果要讲技术，点页面底部的 **Technical details**：里面有证据图谱、规则推理轨迹、原始输出，还可以提问，比如 "what is the root cause"。
6. 备份方案：直接打开 `examples/playground/01-first-scan.html` 到 `03-verified.html`，这三份是提前录好的静态报告。
