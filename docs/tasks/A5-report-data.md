## 为什么要做

评分项"Experiments（定量评估）"和"Business Value（含文献综述）"都要看报告。数据是怎么来的、标签可不可信，老师一定会问（9/28 其他组的 pre 上他反复问"标签从哪来"）。这部分由亲手做数据的人来写最可信，也是你个人贡献最直接的体现。

## 写哪几节（英文，合计约 5–7 页）

### 1. Data（约 2 页）

- **来源总览表**：可以直接改写 [docs/DATA_SOURCES.md](../DATA_SOURCES.md) 的 Overview 表，包括知识来源、215 个生成案例、30 个难例、13 个试调研项目、新的留出项目、BugsInPy、PyDFix、上游回归缺陷。每个来源写清楚：用来做什么，处在训练、开发、测试中的哪个环节。
- **为什么和 proposal 不同**：PyDFix 大部分超出范围，BugsInPy 只有代码缺陷。依据见 DATA_SOURCES.md 的 "What changed from the proposal"。
- **生成数据怎么来的**：5 个模板 × 43 个场景，真实执行，标签来自场景定义；另有 30 个难例只用于评估。具体数字向 B 要最新的。

### 2. Labelling protocol（约 1 页）

- 独立性：谁写规则、谁写标签，冻结前 B 不看；
- 抽样办法：awesome-python，按顺序，按根因分层；
- 标签先于运行：私有仓库提交号，贴在 Issue 里的时间，冻结版本，只跑一次；
- 双人独立标注：一致率和 Cohen's kappa（来自 C1）；
- 打分规则（correct / partial / generic / wrong），以及两人打分的一致率。

### 3. Results on real projects（约 1.5 页）

- **留出结果表**（来自 A3 的 summary）：总成绩和按根因分列。
- **错误分析**：每个非 correct 的项目说明原因，配 1–2 张界面截图。
- **和试调研对比**：试调研第 1 轮是真正的留出（13 个里第一步可用 2 个）；第 2、3 轮不算留出。新一批的数字才是改进后版本的公平成绩。这里要写清楚，不要把第 3 轮的 12/13 当成泛化成绩。
- **真实缺陷验证**（来自 A2）：一共多少个缺陷、多少个库，问题是否在修好后才关闭，有没有给出环境类建议。

### 4. Literature review（约 1.5 页，放在报告前面的 Business Case / Literature Review 部分）

从 proposal 里已有的参考文献开始，补充和"Python 依赖、环境问题"相关的研究。可以从下面这些找起，**每一篇都要自己打开核实**（标题、会议、年份、主要结论），没看过的不要引用：

- PyDFix（Mukherjee 等，ISSTA 2021）：已在 `examples/public-data/README.md` 里；
- BugsInPy（Widyasari 等，ESEC/FSE 2020）；
- Watchman：Python 生态里依赖冲突的监测；
- smartPip：Python 依赖冲突的求解；
- PyEGo：基于知识推断 Python 程序的环境依赖；
- DockerizeMe：推断代码片段的环境依赖；
- SWE-bench：用真实 GitHub issue 评测大模型修代码。

写法：每篇一两句"做了什么"，最后一段说 FixFirst 和它们有什么不同。FixFirst 做的是本地诊断、可追溯的规则和知识、用真实检查验证修复，不自动改代码。
