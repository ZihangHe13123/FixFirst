# FixFirst 首版交付与验收

版本：0.1.0。验收日期：2026-09-08。

本次完成的是可本地安装和运行的 Python 排查工具：终端交互菜单 / CLI + 离线 HTML 报告。入口为根目录的 `启动FixFirst.command`；本机运行环境已配置。源码、示例、数据、实验和队友分工说明均在同一项目目录。

## 已完成的功能

| 功能 | 实际交付 |
|---|---|
| 开始 / 继续排查 | 项目与解释器选择、排查列表、目标切换、暂停 / 恢复 |
| 数据输入 | 环境快照、pip check、pytest 收集、Ruff 检查，以及历史日志导入 |
| 问题整理 | 精确 / TF-IDF / SBERT 归并，原始消息与来源定位 |
| 分类与行动 | 规则基线、可加载 Gini 树、前向推理、前置条件和优先级解释 |
| 修复后的验证 | 新出现、仍存在、未覆盖、待验证、已解决等状态及历史 |
| 输出与分享 | 可搜索、可展开证据的 HTML；JSON；常见路径和凭据脱敏导出 |
| 可复现实验 | 自建故障生成器、30 个已运行案例、模型训练与三种归并方法评测 |
| 团队接手 | README、数据说明、模块流程、实现约定、环境版本记录 |

## 实验结论与尚未证明的内容

测试分区只有 7 条问题级记录，规则分类与 Gini 树 Macro F1 同为 1.0。精确匹配、TF-IDF、SBERT 在该测试分区也给出相同归并结果，只有 3 对正例。**这些结果说明当前受控题目过于简单，不能宣称 AI 模型带来提升。**

5 个项目变体共用相近模板；并非自然开源故障集合。现有分类特征包含解析到的明显故障信号。行动顺序模拟只是检查顺序计数，没有实际用户修复过程，也没有测量节省的时间。

能向队友展示的当前成果是“从日志到下一步行动，再到验证结果”的可运行闭环。需要另行研究的是：在不同结构的真实项目上是否仍然可靠，面对模糊日志模型是否有额外价值，以及用户是否比原有排查方式更快完成任务。

## 明确的产品范围

- 当前自动测试操作只做 pytest 收集，不执行测试体；收集过程仍会执行项目导入与插件。
- pip 一致性通过不能证明运行时导入一定成功；系统保留这一差别。
- 相似症状的归并、规则推导和模型预测都不等于已证实根因。
- 排序是启发式建议，不保证最优修复顺序。用户自己进行源码和依赖修改，再主动验证。
- 支持格式有边界，未识别日志会保留为信息不足；历史导入不会冒充当前项目完整检查。
- macOS / Linux 为当前实现目标，Windows 需要适配文件锁、进程管理和路径后再验收。
- 未建立云服务、账号系统或后台监控；无需外部付费模型 API。

## 交给队友时怎样演示

1. 先看 `examples/demo/01-failure.html`，解释小王看到的两个问题组，以及为什么导入问题优先。
2. 看 `02-partial-check.html`，强调“只重跑代码检查，不能断言测试问题消失”。
3. 看 `03-restored.html`，对照实际完成的测试收集与状态变化。
4. 自己用菜单运行一次完整演示；再按 README 的 A / B / C 分工选择模块。
5. 讨论研究下一步时，以自然故障和用户验证为主，不把已有小样本高分写成普遍效果。

完整本地执行记录位于 `workbench/`，其中 `dataset/` 保留早期依赖案例未捕获的失败尝试；最终完整数据为 `dataset-v2/`。源码包中的 `examples/` 只包含明确标注的最终案例和报告，不包含本机虚拟环境、下载权重或开发缓存。
