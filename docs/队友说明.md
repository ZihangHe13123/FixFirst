# FixFirst 队友说明（v0.6）

v0.3 能跑，但三项课程技术里有两项站不住：决策树的特征就是 parser 已经算好的类别（标签泄漏，F1=1.0 没有意义），"前向推理"只有单跳规则、行动其实是写死的 if/else，知识图谱只是一次排查的溯源记录。v0.4 围绕一个真实问题把三项技术重新组织起来：**同一个异常可能有完全不同的根因，要先判断根因才能给对建议**。v0.5 在此基础上，用 15 个真实开源项目反复检验，把 FixFirst 从"合成数据上好看"推进到"真实项目上可用"。

## v0.6 修复了什么（相对 v0.5）

- Ruff 返回异常或空结果与退出码矛盾时，保留旧问题为未验证，不能当作已修好。
- "Find it" 会考虑早期补丁版，安装建议固定到实际验证过的版本；最多试 12 次，没查完或试装失败时表示无法判定，也不保证找到最新可用版本。
- v0.6 首次发行新增 9 项回归，当时共 141 项通过。Windows 适配增加 8 项，首次复核增加 10 项，第二次增加 19 项，第三次增加 18 项，本次 `r4` 增加 21 项，目前共 217 个用例；本次 Mac 上 216 项通过、1 项 PowerShell 专项跳过。Windows 历史结果与本次修订的验证边界见 `WINDOWS_ADAPTATION.md`。
- Windows 适配的复核修复了按行动 ID 提问时答错行动、带单引号用户名脱敏不完整的问题；两个旧测试显式按 UTF-8 读取 HTML。用户提供的复核记录确认 `r3` 在 Windows 和真正 GBK 环境均 196 项通过，近 1 MB 性能复现约 0.27 秒完成，同时发现路径后诊断字段被吞掉的问题。本次 `r4` 保留 `mode='r'`、`error='permission denied'` 等字段，并覆盖空值、前导空格、双引号值和字段中的第二条路径；性能测试保留继承的依赖路径。用户提供的复核记录确认 `r4` 在 Windows 和真正 GBK 环境均 217 项通过。这些修复已合入仓库，版本号为 v0.6.1。下面的真实项目数字仍是 v0.5 的历史结果，v0.6 尚未重跑新的留出评估。

## 实验结果（写报告、做 pre 用）

详见 `examples/diagnosis-evaluation/REPORT.md`。**主讲“按故障场景留出”这一列**。决策树每折重新训练，但规则和知识图谱保持固定，而且由团队编写；这些受控结果不能代表整个系统对完全未知真实故障的泛化能力：

| 方法 | 按故障场景留出 | 按项目模板留出 |
|---|---|---|
| 只看 parser 类别（v0.3 基线） | 41.9% | 41.9% |
| 规则，不用知识库 | 48.8% | 48.8% |
| 规则 + 知识库 | 79.1%（本数据集上回答时精确率 100%） | 79.1% |
| 规则 + 知识库 + 启发式规则 | 82.8% | 82.8% |
| 只用决策树 | 60.9% | 95.8% |
| **规则 + 知识库 + 启发式规则 + 决策树后备** | **93.0%** | 100% |

三句话讲清楚当前证据支持的作用：

1. **知识库**：有它，规则在它覆盖的故障上准确率 100%；去掉它，规则只剩 7%，混合方法只剩 64%。
2. **决策树**：在知识图谱未覆盖的 145 例中，保持规则、知识与启发式不变，加上决策树后备后准确率从 74.5% 提到 89.7%。69% → 90% 的旧比较同时包含了启发式规则的贡献，不能全算给树。
3. **规则**：在这 215 个受控案例中，规则加知识图谱覆盖 79.1%，给出回答时精确率为 100%；这不保证对其他故障永远正确，也不是规则的独立消融结果。规则判断可追溯到所用证据，有官方来源时附上来源。

**不要讲**"没见过的项目结构 100%"。那一列所有故障类型在训练里都见过，数字好看但说明不了什么，老师一看就会质疑。

## 真实项目测试（报告里很有分量）

详见 `docs/REAL_PROJECTS.md`，用 `scripts/setup_real_projects.sh` 可以重现。三个真实开源项目：

- **humanize**（依赖齐全）：正确判断为"所有测试通过"。
- **humanize（缺测试依赖）**：第 1 轮指出"安装项目声明的 freezegun"。第 2 轮 15 个 benchmark 测试报 `fixture 'benchmark' not found`，第一版没有对应规则，决策树猜成"代码缺陷"，是错的；现在能认出这是 pytest-benchmark 插件没装（规则 D23），装上后全部通过。
- **Flask 1.1.4 + 今天的库**：一开始一个测试都跑不起来。照着 FixFirst 的建议走了 5 轮（jinja2 → markupsafe → itsdangerous → werkzeug → pytest），再加上它后来补的两条建议（pytest<8、装 setuptools），得到 **525 个测试通过，只剩 1 个失败**。这个测试严格要求只记录到 1 条警告，实际记到 4 条：多出的 3 条是 Werkzeug 1.0.1 用了 `ast.Str`，Python 3.12 对它发弃用警告。第一版只看到 `assert 4 == 1`，判成代码缺陷；现在探针会记录测试捕获的警告，FixFirst 能指出来源（`werkzeug/routing.py:957`），建议只统计测试关心的那条警告，或者换 Python 3.11。界面把这类"不影响代码运行"的失败单独列为 Optional，不计入要修的问题数，同时提醒 Python 3.14 会删掉 `ast.Str`，到时 Werkzeug 1.0.1 会真正出错。

这次测试还暴露并修复了 14 个合成数据里没有的问题，比如 conftest 加载失败被当成"不阻碍目标"。这说明合成数据集的局限，也说明拿真实项目验证是必要的。被问到"真实项目上效果怎样"时，就讲这个案例。

## 泛化性检查（13 个没见过的真实项目）

详见 `docs/GENERALISATION.md`。13 个项目覆盖 Web、HTTP、数据可视化、机器学习、命令行、异步、爬虫、数据库等领域，Python 3.9–3.14，平铺 / src / 单文件布局。**先人工标注正确答案并提交到 git，再运行 FixFirst**，只给 FixFirst 的第一步打分。

| | 第 1 轮（留出，代码未改） | 第 2 轮（修了普遍性原因） | 第 3 轮（加了"试装找版本"和读锁文件） |
|---|---|---|---|
| 第一步正确 | 2 | 9（其中 2 个依赖第 1 轮之后补的知识） | 12 |
| 部分正确 | 3 | 2 | 0 |
| 只给通用建议 | 3 | 2 | 1 |
| 错误 | 5 | 0 | 0 |

第 3 轮新增的两项：
- **试装找版本**（`versions.py`）：缺某个名字时，用户点 "Find it"，FixFirst 在临时环境里按版本系列试装（先退 1、2、4、8 个系列，再二分，最多 12 次），找到仍有这个名字的最新版本，给出精确的安装命令。Flask 2 次、Django 6 次、scikit-learn 5 次就找到了。这是课程第四类技术（搜索）的部分实现，报告里如实写"部分"，不是 A*。
- **读锁文件**：Pipfile.lock / poetry.lock / uv.lock 记录了项目当年测过的版本。records 的锁文件写着 SQLAlchemy 1.2.6，环境里是 2.0.54，于是建议回到 1.2 系列，验证过有效。

讲法：**第 1 轮才是泛化性的真实数字**（13 个里第一步可用的只有 2 个，原因判断对的有 6 个），和合成数据上的 93% 差距很大，说明真实项目难得多；第 2 轮说明这些失败都有普遍原因（FixFirst 自己在 Python 3.9 上崩、没读 setup.py、把 pip 装 Python 当建议……），修复时没有针对单个项目写特例，而且合成数据集的评估结果完全不变。要公平衡量改进后的版本，需要一批新项目，最好由作者以外的人挑。

## 答辩可能被问到的问题

1. **"决策树用什么特征？"** 44 个从原始证据提取的特征，列表在 `evidence.FEATURE_NAMES`，最终那棵树可以直接打开 `decision_tree.txt` 看。特征里没有 parser 的类别，也没有标签。
2. **"规则是你们自己写的，数据也是你们自己造的，不是循环吗？"** 是的，所以要看"知识库没覆盖"那一栏和"没见过的故障类型"那个协议，报告里也明确写了规则分数偏乐观。决策树每一折都重新训练，而且不包含被留出的那一组。
3. **"为什么不直接用 ChatGPT？"** FixFirst 在本地运行；每条结论都能追溯到检查记录和官方 release notes；知识库没有依据时，只把模型的判断作为"待确认线索"，排在有证据的建议后面，不会编造。
4. **"真实项目上效果怎样？"** 先讲 13 个项目的留出检查：第 1 轮只有 2 个第一步可用，原因判断对的有 6 个，这才是泛化性的真实数字；失败都有普遍原因，修复后是 12/13，但那一轮不算留出。再讲 Flask 1.1.4 的案例：从一个测试都跑不起来到 525 个通过。用户研究还没做，这是接下来的重点。
6. **"找版本那个功能会不会把用户环境搞坏？"** 不会：只在用户点 "Find it" 时运行，在临时目录里建一个同版本 Python 的环境，只装预编译的 wheel（不运行任何构建脚本），用完删除；用户自己的环境不动。
5. **"失败案例呢？"** 报告最后一节列了：普通字典的 KeyError 被判成缺配置、有 bug 的 fixture、被整个移除的库子模块。

## 每个人要读懂的部分

纯靠 AI 写的代码最大的风险，是答辩和个人反思时说不清楚。每人至少读懂自己这一块，能在白板上讲出一个例子：

| 负责人 | 必须读懂 | 能讲清楚的例子 |
|---|---|---|
| A：数据与证据 | `evidence.py`、`diagnosis_cases.py`、`runner.py`、`probe.py` | 一个 `KeyError` 是怎么被判断为"os.environ 查找"的；数据集的一个案例是怎么生成的 |
| B：推理与模型 | `engine.py`、`rules.toml`、`reasoning.py`、`classification.py`、`evaluation.py` | 规则 D02 怎样匹配 `numpy.float`；为什么否定条件要分层；两种交叉验证有什么区别 |
| C：知识与界面 | `domain.toml`、`domain.py`、`knowledge_graph.py`、`web.py`、`report.py` | 一个建议是怎么追溯到 Python 官方文档的；Web 界面怎样防止其他网页调用它 |

## pre 现场演示（约 2 分钟）

1. 运行 `.venv/bin/fixfirst serve`，在首页点 **Open a sample project**。
2. 讲解：页面顶部一句话说明现状（"2 problems to fix"）；下面按顺序列出要做的事，每一步都写明**改哪个文件第几行**（比如 `pricing.py:1`）、根因和改法。可以展开第 1 步的 "Details"，展示判断它的规则和 Python 官方文档链接。
3. 按 `FIXES.md` 改两行代码，点 **Check again**：这两个问题进入 "Fixed and verified"，同时出现两个之前被挡住的运行期错误。强调一点：只有真实检查通过才算修好。
4. 改完剩下两处，再点 **Check again**，页面显示 "✓ All tests pass"。
5. 如果要讲技术，点页面底部的 **Technical details**：里面有证据图谱、规则推理轨迹、原始输出，还可以提问，比如 "what is the root cause"。
6. 备份方案：直接打开 `examples/playground/01-first-scan.html` 到 `03-verified.html`，这三份是提前录好的静态报告。
