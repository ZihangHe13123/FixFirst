# FixFirst v0.3：给队友的讨论与验收说明

现在是可以在本机实际排查 Python 项目的课程原型：选择项目与解释器，运行检查，得到有出处的行动清单，手动处理后重新验证。交互入口是终端菜单，HTML 报告可离线分享。v0.3 做了三轮有实际运行验证的优化。

## 三轮分别解决了什么

| 场景 / Pain Point | Feature | 现在可以看到的结果 |
|---|---|---|
| 小王运行 pip check 没问题，但项目声明的依赖没装或版本不符 | 项目声明与目标环境对照 | 精确指出 `requirements.txt:1` 声明 `packaging>=24.2`，实际安装 `24.1`；可选项、条件依赖与必需项分开判断 |
| 队友担心演示只是人为编造，换项目就失效 | 可离线复算的官方历史回归 | Packaging 两例、Click 两例；保留官方修复链接、提交号、wheel 来源、SHA256、许可证、故障及恢复记录 |
| 一大段 traceback 看不懂，也不确定模型说得对不对 | 实际异常类型、抛出文件与行号、模型分歧提示 | `InvalidVersion` 从 1874 字符的 traceback 摘取为 42 字符的实际异常；完整输出仍保存。旧模型误判被明确展示 |

声明冲突会排在重复验证前；它是否导致某个断言失败仍需通过修复后的测试判断。没有导入故障时，不再生成无关的导入路径建议。删除依赖声明、删除测试或跳过测试都不充当原问题修复证据。

## 十分钟内给队友看什么

1. 打开 `examples/dependency-demo/01-broken.html`，看声明、实际版本和下一步行动；在图谱中选择该行动，追溯到声明检查。
2. 打开同目录 `02-fixed.html`，看原声明满足、测试通过和问题关闭。该演示在历史缺陷上加入了我们编写的版本约束，**不另算一个自然缺陷**。
3. 打开 `examples/historical-regressions/packaging-full-version/03-model-disagreement.html`：实际异常是 `InvalidVersion`，模型却候选为 `import_failure`；行动仍是检查运行异常。
4. 使用 README 的 `historical` 命令，在自己的新目录离线复现四例。首次安装 FixFirst 本身需要网络；历史实验用随包 wheel。

## 数据和实验结论

| 数据 | 来源与数量 | 可以支持什么 | 不能支持什么 |
|---|---|---|---|
| v0.1 / v0.2 受控数据 | 60 个自建案例、70 条问题标签、540 个历史检查 Run；模板相近 | 训练、归并及状态闭环的可重复实验 | 不代表真实故障分布或独立真实项目 |
| v0.3 历史缺陷 | 两个官方第三方库、四个历史缺陷的最小复现 | 在真实库版本上复现失败、正确恢复、解析自然 traceback | 不等于完整上游测试套件或大规模自然数据集 |
| v0.3 声明演示 | 1 个受控声明不一致场景，复用已计数的 Packaging 缺陷 | 展示 pip check 与项目声明检查的互补、声明问题关闭 | 不增加自然缺陷数量 |

四个历史缺陷：

- [Packaging #788 / 修复 #794](https://github.com/pypa/packaging/pull/794)：预发布范围判断；24.1 失败，24.2 通过。
- [Packaging #678 / 修复 #825](https://github.com/pypa/packaging/pull/825)：外部传入的 Python 版本尾随 `+`；24.1 失败，24.2 通过。
- [Click #2500 / 修复 #2724](https://github.com/pallets/click/pull/2724)：帮助文本遗漏空字符串默认值；8.1.7 失败，8.1.8 通过。
- [Click #2632 / 修复 #2730](https://github.com/pallets/click/pull/2730)：帮助文本没反映 default_map；8.1.7 失败，8.1.8 通过。

同一例从失败到通过没有修改测试源码；只切换官方库版本，实际检查了安装版本。这四例故障版本中的 pip check 均通过，说明“已安装包的约束相容”和“功能没有 bug”是不同的验证任务。每例至少保存完整环境、pip check、测试执行和声明检查两个阶段的记录。

在固定旧模型、未重新训练的四例测试上：规则 4/4 正确，Gini 3/4 正确。Macro F1 分别为 1.0 和 0.333，后者按真实和预测标签并集的三类计算。错误是把测试体里的普通运行异常误判为导入失败；原训练数据中普通运行异常主要发生在 setup / teardown，模型学到了不可靠的阶段关联。这是从训练集结构与树分支作出的解释，不是对所有决策树的结论。不要用四例小样本宣称规则普遍更好，也不要为了这四例改完模型后仍称它们为未见测试集。

目前没有真人试用数据，不能宣称节省了百分之多少调试时间。自然案例的归并只有很少正例，本轮未用它们宣称语义模型有效。

## 三个人怎样继续分工

| 负责人 | 可直接接手的模块 | 下一项有价值的工作 | 验收标准 |
|---|---|---|---|
| A：数据与诊断 | `project.py`、`probe.py`、`parsers.py`、`historical_cases.py` | 找其他结构的开源项目历史故障；扩展明确缺失的声明格式 | 来源、版本、许可、故障与恢复命令齐全；在独立环境实际失败再通过 |
| B：算法与实验 | `grouping.py`、`classification.py`、`reasoning.py`、`knowledge_graph.py` | 增加不同阶段的普通异常训练样本与困难归并；保留新的未见项目测试集 | 比较规则与模型、记录误判与拒判；不能靠从标签直接复制特征证明增益 |
| C：产品与整合 | `cli.py`、`interactive.py`、`service.py`、`report.py` | 组织同学试用同等难度任务，改进建议顺序与术语；整理组报告与真人演示 | 记录任务成功、操作数、耗时及失败原因；版本、说明和复现命令一致 |

建议本周讨论重点：先把目标用户固定为接手或启动 Python 项目的初学者；选 2–3 种常见工程结构做真实试用；决定如何增加算法的可验证价值。暂不扩展多语言 IDE、自动改代码或自由聊天服务。

## 课程与验收边界

实际技术组仍为规则推理、知识发现 / 数据挖掘、证据知识图谱。没有把启发式排序称为 A* 或遗传算法；TF-IDF 与 Gini 也不拆成两个组。具体课程要求见 `COURSE_ALIGNMENT.md`，最终归类需要教师确认。

本轮自动化检查为 80 项通过，包含真实子进程、旧功能回归、声明边界、异常链、凭据脱敏及模型分歧。另做新环境 wheel 安装和离线历史复现，以及桌面 / 窄屏报告检查。仅在 macOS Apple Silicon、Python 3.12 实机验收；Linux 未在本轮实机执行，Windows 原生暂不支持。

proposal、最终组报告、两段各五分钟视频、个人反思和 Canvas 提交属于小组仍需完成的课程工作。软件版本发布不代表已经提交或已经评分。
