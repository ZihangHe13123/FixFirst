- **不用语言模型或付费 API。** 需要账号、密钥、付费服务、GPU 或大文件下载的项目，都按排除规则跳过。

## 每个项目怎么跑

1. **安装**：严格照 README 或仓库里的依赖文件装。固定版本装不上时，记录原始报错，再改用"去掉版本号、装最新版"。这是新手最常见的做法，作为偏差记录下来。
2. **目标**：
   - notebook：所有单元格依次执行完、不报错（`--goal run_project --notebook`）；
   - 脚本：按 README 的示例命令运行成功（`--script`，加 `--arg`）；
   - 应用：按 README 执行测试。pytest 用 `pass_tests`，unittest 用 `pass_unittest`。没有测试的，用 README 里有限时间内会结束的启动或配置命令（例如 `manage.py migrate`、`manage.py check`），不用会一直运行的服务器命令。
3. **基线**：先不用 FixFirst，照 README 原样运行一次，记录第一个失败。
4. **FixFirst 循环**：每一轮执行 `fixfirst scan`，读出第一个必须修的步骤，先分级，再照做，然后重新 scan。
   - 分级：
     - **完全满足**：给出命令，或者给出具体位置和改法；
     - **部分指导**：原因和改法类型对，但细节要从错误信息里补；
     - **通用建议**：只是让人去检查；
     - **错误**：照做没有用；
     - **有害**：会破坏环境或测试。
   - 执行方式：给出命令的原样执行；给出具体改法的照改；部分指导由我用错误信息补全，记为"辅助"；通用建议由我自行判断修法，记为"人工"，不算 FixFirst 的功劳。
5. **停止条件**：达成目标；FixFirst 引导的轮数达到 10 轮，或花满 60 分钟；遇到超出范围的阻碍（系统库、编译器、凭据、数据源不可用）。
6. **完整性**：不删除单元格或测试，不跳过测试，不放宽断言，不改变 notebook 预期的输出含义。每一处改动都保存 diff。

**汇总（8 个）**：
- **健康项目 3 个**：全部没有误报，状态都是 done。其中 2 个有非阻塞的声明噪音。
- **有故障的 5 个**（N2、S2、C1、C2、C3）：只靠 FixFirst 的引导跑通的只有 S2 这 1 个；靠人工修复跑通的 2 个（N2、C3）；10 轮内没跑通的 2 个（C1、C2）。
- **第一层根因**：S2、C3、N3 判对；C1 按表面症状（缺依赖）判对，但不知道真正的原因是安装失败；N2 没有给出结论；C2 第一层只给了通用建议。
- **出现过的错误或有副作用的步骤**：没有破坏数据的有害步骤。但有 5 类步骤让环境变得更糟：
  - 不设上限的升级把版本冲过头（C2、C3）；
  - 版本搜索只验证缺失的名称，不看项目其他已声明的约束（C3 的 1.5.12；C2 的 1.4.54 和 Flask-SQLAlchemy 3.1 冲突）；
  - 对新增的名称去找更老的版本（C2）；
  - CLI 列出针对已消失问题的过时动作（C2）；
  - 备选方案在当前 Python 上装不上（S2）。

**需要改进的地方，按对"能否跑通"的影响排序**：
1. 版本调整要考虑约束：
   - 升级要设上界，并参考 pip check 和项目已声明的版本；
   - 版本搜索要验证项目整体（其他已声明的依赖），不能只验证缺失的那个名称；
   - 缺失的名称如果是更新版本才新增的，应该往新版本方向找。
2. 安装阶段：
   - 缺多个已声明依赖时，一次给出全部安装命令；
   - 能读取 pip 安装失败的输出；
   - 支持 `environment.yml`；
   - 不给在当前 Python 上装不上的备选方案。
3. 整套依赖明显早于当前解释器时（例如 README 要求 Python 3.5，或固定的库不支持 3.12），把"换较老的 Python"作为正式步骤给出。
4. CLI 缺陷：不要列出针对 not_observed issue 的过时动作。
5. notebook：定位到定义函数的单元格；检测前面单元格里静默失败的 `!` shell 命令。
6. 知识覆盖：notebook/脚本模式不使用决策树，常见库变化（例如 matplotlib 的样式名、只能用关键字的参数）要靠知识库补上。
7. 输出噪音：init/scan 时会打印项目文件的 SyntaxWarning。
