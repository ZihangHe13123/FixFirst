## 评价尺度

**每一层失败，只评 FixFirst 的第一步**：

| 等级 | 含义 |
|---|---|
| 完全可执行 | 给出命令，或给出准确位置和具体改法，照做即可 |
| 部分需解释 | 原因和改法类型对，但细节要从错误信息或测试里推出来 |
| 通用 | 只是让人去检查 |
| 错误 | 照做没有帮助 |

另外单独标记"有副作用"：照做以后环境变得更糟。

**每个项目只记一种结果，彼此互斥**：

| 代号 | 含义 |
|---|---|
| M1 | 只执行"完全可执行"的步骤就跑通 |
| M2 | 还用到了"部分需解释"的步骤，由操作者按步骤说明补全细节 |
| H | 中途至少有一次人工兜底（在通用或错误步骤之后，由操作者自己决定修法）后跑通 |
| N | 预算内没有跑通 |
| U | 未知、超时或下载未完成 |

**健康项目**：如果目标能跑通，却报了必须修的问题，算误报。非阻塞的噪音另外记录。

## 审核说明（追加；原日志和原判断不变）

1. **R-N3 的定性要收窄。** 默认的 nbconvert 按 notebook 元数据去找 `conda-root-py` kernel，所以失败了；而 FixFirst 明确使用项目的 Python，并且成功执行。因此这是"内核配置和可移植性没有提示"的缺口，不应算作 FixFirst 在检查所选解释器时漏报。
2. **R-N1 的范围差异。** "把故意演示的报错当作预期结果"这个判断虽然在扫描前就写好了，但它放宽了"无错误执行"的运行契约：RETEST.md 的目标写的是"全部单元格执行完"，第一批 README 写的是"不报错"。所以 R-N1 的"健康、误报 1 次"只在放宽后的契约下成立。按严格契约，不改教材本意就完成不了这个任务，结果应单独看待。
3. **新批次不能证明第六轮安装建议的改进。** 新批次里，固定版本装不上时，按协议先改装了无固定版本的最新包（R-N1、R-N2 的 NumPy），再交给 FixFirst，所以没有经过第六轮的安装建议。下面的第一批配对回归沿用原协议：C1、C2 在安装失败后直接扫描。带导入日志的第六轮工作流单独作为补充轨迹记录。

4. **旧的使用方固定版本卡住时，指不出该改谁。** 例如 `Flask_SQLAlchemy==2.2` 需要依赖里已删除的名称：FixFirst 只在约束范围内搜索提供该名称的包（结果为 not_found），或者只能试已声明的旧版（结果为 inconclusive），都没有指出应该升级这个使用方。
5. **缺少迁移知识**：Flask-SQLAlchemy 3 的 `Model` 位置、Flask-JWT-Extended 4 的 `jwt_optional`、Django 1.10 在 Python 3.8 以上的 `__classcell__`，以及 N2 的 matplotlib 样式改名和 `Ellipse` 的 angle 参数。
