# 打分规则（A2 第 4 步工作稿）

把卡片第 4 步的四个档位展开成可以逐行执行的判定流程。**规则本身可以两人共用**（不共用的是分数）。
标注为【卡片】的来自 `docs/tasks/A2-heldout-run.md` 第 81–110 行；标注为【本稿】的是卡片没写死、
容易在 agree 时吵起来的地方，打分前应当确认一遍口径。

## 0. 打分对象

- **只给第一步打分**，取 `fixfirst_first_step` 列 —— 新用户读完页面后第一件会去做的事。【卡片】
- 只有用了 Find it 的行才需要看 `search_offered`（搜索**之前**那一步在那儿）。
- 判断依据只有两样：**本行的标签列** 和 **FixFirst 的输出列**。不为了替它辩解去翻源码或 git 历史。
- **不改 `labels.csv`。** 标签和实际不符时写进 `notes`，报告另按
  `examples/real-world/LABELS.md` 的 Corrections 一节处理。【卡片 21】

合法取值只有四个：`correct` / `partial` / `generic` / `wrong`（`scripts/heldout.py:56`，
比较时按小写去空格，`summary` 会把没填的行列成 not scored，所以别用近义词）。

## 1. 两个轴

- **轴 A｜原因对不对**：第一步有没有点出本行标签的那个**具体东西**——具名。
  - 算具名：说得出名字的包/依赖、模块或函数、配置变量、版本边界、平台差异。
  - 不算具名："读原始输出手动排查"、"检查一下这个异常"、"检查工具是否可用"、
    "比较期望值和实际值"、"检查依赖声明"。
- **轴 B｜照做行不行**：执行它给的动作/命令，**这一层**问题会不会消失。
  （后面还剩几层不影响判定。）

## 2. 判定表（按顺序判，先命中先定）

**第一步：健康项目**（`label_root_cause = healthy`）

| 情况 | score |
|---|---|
| FixFirst 给的是 `(no must-fix step)` | `correct` |
| 任何形式地"必须修" | `wrong` |

没有中间档。【卡片 108】

**第二步：非健康项目**，按下面的顺序对照，先命中先定：

| 顺序 | 情况 | score |
|---|---|---|
| 1 | 命中本行 `wrong_if`（指向别的原因 / 改别的地方 / 跳过或改测试） | `wrong` |
| 2 | 轴 A 不成立（没点出原因，只有通用建议或纯动作） | `generic` |
| 3 | 轴 A 成立，但轴 B 不成立（照做不够 / 跑不通 / 命中 `partial_if`） | `partial` |
| 4 | 轴 A、轴 B 都成立（语义等同 `first_step` 或 `also_acceptable`） | `correct` |

三条优先级（【本稿】，这是最容易分歧的地方）：

- **`wrong_if` 优先于 `partial_if`。** 指向了别的原因就是 `wrong`，哪怕它顺带做了一件有用的事。
  轴 A 错了，轴 B 对了也不算对。
- **`generic` 优先于 `partial`。** 没说出原因就是 `generic`；只说"可能要看看 X"而 X 不具名也是
  `generic`。`partial` 的前提是原因说对了，只是动作不够。
- **`correct` 和 `partial` 的界线只在轴 B。** 原因说对了，但版本界线给得过宽（只说"升级到兼容版本"
  不说升到哪）、或命令在本机装不上 → `partial`。【卡片 104 的两个例子就是这个意思】
- **`wrong` 和 `generic` 的界线在"原因类别"。** `fixfirst_cause` 的类别跟标签的 `root_cause` 一致、
  只是第一步不具名 → `generic`；类别本身就不对（且落在该行 `wrong_if` 里）→ `wrong`。
  例：标签是 `code_defect`、FF 说 "Defect in project code or tests" → 类别对 → `generic`；
  标签是 `version_incompatibility`、FF 也说 "Defect in project code or tests" → 类别错 → `wrong`。
  同一批里必须这样分开，否则两种性质完全不同的问题会被并成一档。【本稿 2026-10-02】

## 3. 边界情形

| 情形 | 怎么判 |
|---|---|
| `fixfirst_hedged = yes`（只说"可能是"） | 不影响档位。说对了照样 `correct`，notes 记"仅以可能/推测语气给出"。【卡片 103】但 **hedged + 不具名 = generic**。【本稿】 |
| `fixfirst_rules = F01` | F01 的定义是"没有规则命中，由标注案例训练的决策树给出的**猜测**"（`src/fixfirst/knowledge/rules.toml:626`）。卡片没给它单独档位，所以**不改变档位**；但 notes 必须写"F01，无规则支撑的统计猜测"，因为报告要区分"诊断出来"和"猜中了"。【本稿】 |
| 给了多步 | 只看第一步，第二步对不算数（写进 notes 备查）。【卡片 99】 |
| headline 说对了、第一步是"自己查" | **以第一步为准**，按 generic/wrong 判，notes 记 headline 说对了。【本稿】 |
| 原因类别对、具名对象错（说 missing_dependency 但点错包） | 轴 A 不成立。还给了可执行动作 → `generic`；直接指向另一个具体原因 → `wrong`。notes 说明。【本稿】 |
| 标签自相矛盾，或按 `first_step` 照做其实清不掉这一层 | 不改标签。按最接近的档位打，notes 写明"标签与实际不符"，必要时引 `wrong_if` 里已经预言的那条。【本稿】 |

## 4. notes 的写法

固定成三段，方便两人逐条对齐：

```
<命中哪一列 / 为什么> + <证据> + <保留意见>
```

例（结构示范，不是对任何具体项目的判定）：

- `partial_if 命中（只设了变量没初始化）—— twin 第 1 步已证明后一层错误仍在；hedged`
- `wrong_if 命中（建议改项目代码）—— 标签 first_step 是改解释器/版本`
- `F01，无规则支撑的猜测；具名了具体包，但语气是"可能"`

**每条至少引一件证据**：标签的哪一列、原输出的哪一行、或 twin 的第几步。没证据的判断在 agree
时最容易被对方推翻。

## 5. 拿不准时的取证

卡片把 twin 实验称为"最有说服力的依据"【卡片 109】。

- 做法：`heldout.py twin` 复制一个项目 → **只**实施标签里的 `first_step` → 看原失败是否消失。
- **只有轴 B 含糊时才需要做。** 轴 A 含糊（是不是 generic）不用跑实验，回去看措辞具不具名就够。
- 结论写成 notes 里的一行，例如"twin: 照做后 X 的错误从 N 降到 0"或"仍然存在"。
- 实验只在**副本**里做，不动 `~/heldout-projects`（环境不重建）。【卡片 环境条款】

## 6. 独立性与自查

- 打分期间**不看、不讨论** `scores-C.csv`。
- 先给三个锚点行定型（一个明显 correct、一个 generic、一个明显 wrong），再往下打；
  打完把前三个重打一遍，看有没有飘。
- 打完只看自己的 `summary` 分布，**不要据此回头调分**——那是第 5 步的事。若某一档扎堆，
  回头核对是不是把"具名"的门槛放松了。
- 第 7 步给大模型基线打分时**用同一套规则**，只是 `scored_by` 换人、项目名换成 `model-1`、
  `model-2`。【卡片 156–158】
