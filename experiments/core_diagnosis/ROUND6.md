## 已完成的机制修复

1. 合并项目声明和目标解释器中的已安装依赖要求，按目标 markers 和显式 extras 处理。
   识别下限意味着应该升级的情况，避免遇到缺少名字就一律向旧版本搜索。
2. 搜索只考虑满足已知约束的候选；试验每个版本时重建环境，并保留其他依赖限制。
   环境或声明变化后，旧结果失效。搜索验证的 API 存在性不代表完整项目通过。
3. 多个已声明必需依赖缺失时，一次提出整组安装要求；不默认开启可选组。
   导入的 pip 日志能对应到失败包、固定版本及声明位置，不静默绕过项目 pin。
4. 对矛盾或装不上的固定版本，提供显式 **Try a dependency set** 检查。它在临时环境中
   提议放宽一个被点名包的版本限制，保留其余项目声明；相关间接依赖共同解析。已安装的包即使不再被新版本依赖，也保留为试验请求，防止试验环境里消失、原环境却留下冲突。依赖图
   之外的已安装包保持版本。结果给出精确声明改法、整组安装版本和依赖一致性检查。
5. 上述试验只安装 wheel，最多 300 秒，不改变原项目或环境。成功只表示安装/元数据检查
   通过，原程序和测试仍待运行。因 wheel 限制失败时点明真正卡住的包，不归咎于其他包或
   Python。配置文件里的 pip/uv 索引设置不沿用，环境索引设置仍有效，此边界会显示在步骤中。
6. 静态读取 `environment.yml` / `.yaml`：明确区分 pip 子列表、8 个有官方来源的 PyPI
   替代名与未转换的 Conda 名称/构建/channel 条目。README 等 Python 版本是有出处的线索，
   不被当作可用环境或自动下载承诺。
7. 不再用当前版本为未观察到的旧问题重新生成过时修法；CLI 与网页使用相同的动作排序
   和折叠结果。历史失败与待验证记录继续保留。

  这是人工解读的预期输出，不能从已有报错输出自动推导“应该忽略”。
- 唯一仍有非预期运行故障的任务 R-S3，缺少两项 NLTK 数据。两个第一步都是通用建议；
  FixFirst 引导的 M1、M1+M2 均为 **0/1**，人工下载后 H 为 **1/1**。不能把后者记为工具修复成功。

  原报告的“漏报”作为内核配置/可移植性提示缺口单列，不能直接算所选解释器检查的假阴性。

## 尚未解决

- 不能保证多层旧项目一路跑通。当前例 C 证明了实际安装路线仍可能超出 wheel 试验范围。
- 安装元数据一致不保证 API 或行为兼容；升级后必须运行原检查。
- 不完整的静态声明、私有索引和源码构建可能需要人工处理。
- 默认决策树与候选模型没有因本轮重新训练。改进来自证据、约束、解析与建议执行流程。
- 新批次暴露的 NLTK 数据建议、notebook 预期错误表达和内核配置提示缺口尚未实现。
- 用户研究、强模型对照与独立留出评估仍需分别完成。
