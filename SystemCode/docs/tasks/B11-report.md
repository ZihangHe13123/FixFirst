## 各章写什么

### 商业价值和市场（约 3 页）

- **痛点和数据**：
  - PyDFix 重建的 2,702 个真实构建里，1,921 个（71.1%）因为依赖错误无法复现（[DATA_SOURCES.md](../DATA_SOURCES.md)）；
  - 试调研的 13 个开源项目，按自己的说明安装后，12 个的测试跑不通（[GENERALISATION.md](../GENERALISATION.md)）；
  - Python 每年发布一个新版本（PEP 602），旧的模块和 API 会被陆续删掉。
- **谁会用**：接手旧项目的开发者、课程里的学生和助教、复现论文代码的研究人员、给新贡献者排错的开源维护者、遗留 Python 系统多的企业。
- **价值**：更快找到根因；不乱改代码；在本地运行；每条建议都能追溯到证据和官方文档；修好要经过真实检查才算。
- **现有工具对比表**：至少 6 个，每个写它做什么、不做什么、和 FixFirst 的区别：
  - `pip check` / pip 的依赖解析；
  - pipdeptree；
  - Dependabot / Renovate；
  - tox / nox；
  - IDE 的检查；
  - 通用 AI 助手。

  和 AI 助手的差别要写清楚：FixFirst 能追溯、会验证，还能作为 MCP 工具给 AI 助手用，两者是互补的。
- **定价**：Community 免费开源；Pro 按月订阅，含每月更新的知识库；Team 按席位，含 CI 集成和共享规则；Education 免费或优惠。宣传视频（[B16](B16-promo-video.md)）要用同一套说法；引用竞品价格时写明查询日期和链接。
- **文献综述**：从 proposal 里已有的参考文献开始，补充 Python 依赖和环境问题相关的研究。可以从这些找起：
  - PyDFix（ISSTA 2021）；
  - BugsInPy（ESEC/FSE 2020）；
  - Watchman；
  - smartPip；
  - PyEGo；
  - DockerizeMe；
  - SWE-bench。

  **每篇都要亲自打开核实**标题、会议、年份和结论，没看过的不引用。最后一段写 FixFirst 和它们有什么不同。

### 数据和标注（约 2 页）

- **来源总览**：可以改写 DATA_SOURCES.md 的 Overview 表。每个来源写清楚：用来做什么，处在训练、开发、测试中的哪个环节。还要写和 proposal 相比为什么变了。
- **生成数据**：5 个模板 × 43 个场景，另有 30 个难例；标签来自场景定义。
- **留出项目的标注流程**：
  - 独立性：规则由 B 写，标签由 A 写，C 独立复核，冻结前 B 看不到；
  - 抽样办法；
  - 标签先于运行：私有仓库的提交号在 Issue 里公开，冻结版本只跑一次；
  - AI 辅助排查的模型、用途、案例数量、人工核查及副本验证方式；不能将 AI 辅助标注写成全程纯人工；
  - 初始判断的一致率和 Cohen's kappa、共同可比较的案例数 m/N，以及后续共同裁决、排除/替换的数量与原因；不能用看过对方答案后的结果计算独立一致率；
  - 打分规则，以及 A、C 打分的一致率。

### 实验和结果（约 5 页）

- **生成数据**（[B6](B-tasks.md)）：按故障场景留出的结果、基线、消融；难例集。明确说明：LOTO 的 100% 和难例上的 15/30 都不是留出结果。
- **新的真实项目**（[A2](A2-heldout-run.md) 的结果）：
  - 总成绩和按根因分列的结果；
  - 每个没做对的项目的错误分析，配 1–2 张截图；
  - 和试调研第 1 轮（2/13）对比。第 2、3 轮不算留出结果。
- **真实缺陷验证**（[B12](B12-bugsinpy.md)）：加上 4 个上游回归缺陷，一共多少个缺陷、多少个库；问题是否在修好后才关闭；有没有给出环境类建议。
- **基线**：
  - 一次性诊断（[B3](B-tasks.md)）：本地大模型的根因和第一步，第一步由 A、C 打分；
  - agent 修复对比（B7）。
- **分组**（B9）。
- **用户研究**（[B13](B13-user-study-design.md)、[C2](C2-user-study-sessions.md)）：
  - 方法、参与者；
  - 完成率、用时、SUS；
  - 和 proposal 目标的差距；
  - 效度威胁：人数少、学习效应、任务是人为构造的、实验员是组员。
