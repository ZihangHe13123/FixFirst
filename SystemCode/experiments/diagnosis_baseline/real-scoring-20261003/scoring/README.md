# B3 真实项目：独立第一步评分说明

这是一次性诊断回答的人工评分。每个匿名模型有 12 个项目。评分者只收到自己的 A 或 C 表，模型身份映射由 B 单独保管，待评分和分歧对齐完成后再揭示。

## 填什么

- 只填 `score`、`scored_by`、`notes` 三列。不要改项目 ID、参考标准、模型回答、答案状态或其他列。
- 有实际回答的行，`score` 使用 A2 已约定的 `correct`、`partial`、`generic`、`wrong` 四值，结合每行的参考第一步及可接受/部分/错误条件评分。根因类别相同不自动表示第一步正确。
- 健康项目按该行的无修复标准判断。不要因为缺少检查证据就认定健康。
- 随包的 `unavailable-answers.csv` 按匿名模型和项目 ID 标出 **5 条 `service_no_answer`**。这 5 条没有实际建议：保留该行，`score` 留空，填写 `scored_by`，并在 `notes` 写 `service_no_answer：已核对无可用回答`。不要将其填为 `wrong`，也不能当作模型说“无需修复”。本批其余 31 条都有实际回答，按上述四值评分。
- 技术缺答仍计入 36 次请求（每模型 12 次）的总分母，服务可用率单列；第一步内容质量的分母须明确写成有实际回答的数量。如果另报每次请求取得正确建议的比例，技术缺答计为未取得正确建议，但不改写为“建议方向错误”。不得删除、重试或用新回答替换这些行。
- 如标签或标准有争议，在 `notes` 里说明，不依据某模型答案改冻结标签。
- 如果回答自报了模型身份或另有破盲迹象，保持原文，在 `notes` 标记。

## 顺序

1. A、C 各自独立完成三张表，不互看对方分数。
2. 每表应有 12 个唯一项目 ID，`scored_by` 均不能为空。有回答行必须填四值评分；技术缺答行按上述说明留空并确认。空分只有同时匹配 `unavailable-answers.csv` 和人工确认才算处理完成，否则是漏评。
3. 将原表交回 B 保留，再按匿名模型逐一核对分歧，另存对齐说明及最终共识表；不要覆盖原独立评分。
4. 空表不运行一致率统计；空字符串一致不代表完成评分。收到完整表后，内容评分一致率仅在有实际回答的相同行上计算，技术缺答的确认另外核对；不要把这 5 个空分算成五次评分一致。

## 比较范围

这些回答基于原 A2 初始检查记录的有界、脱敏呈现；每次为无工具的新请求。A2 的 FixFirst 第一条建议允许来自 Find it 后的状态，因此两者的工具条件不同。B3 不重跑原项目，也不把模型建议的文字等同于已经执行并修好。

根因诊断指标、健康项目表现和人工第一步质量分别报告。此包不包含模型真实身份、原服务响应、运行配置或自动预填的分数。
