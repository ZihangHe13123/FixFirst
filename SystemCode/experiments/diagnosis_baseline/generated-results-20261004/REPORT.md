# B3：冻结生成案例与困难开发案例的同证据对照

2026-10-04。状态：750 条模型回答已封存；两版 FixFirst 离线对照、独立复算和报告完成。

## 结论

本次表格评估**根因类别**，不评估第一步建议质量或修复成功。FixFirst v0.7.0 在本批普通/困难案例均答对；v0.8 候选在普通集少 5 个有效诊断，困难集保持一致。三个本地大模型中，Qwen3.8 的类别准确率最高，同时耗时更长。

这是已用于训练或开发的受控场景，**不能由此断言 FixFirst 在未见真实项目上胜过大模型**。大模型没有接收标签、FixFirst 诊断结论或其知识库；FixFirst 本身使用既有模型、知识和规则，受过本类开发数据影响。

## 3. v0.8 为什么少了五例

五个模板的 `vi_unittest_alias` 旧记录没有接收对象的归属信息。v0.7.0 给出版本不兼容；v0.8 为避免把同名项目类误判成库 API 移除，要求重新采集，实际主诊断为空。

**在这张旧输入表里，v0.8 确实少答对 5 例，普通准确率下降约 2.27 个百分点。** 按登记将五例计未答、计错；不根据注入真值补归属信息，不拿之前新采集回归的正确答案替换它们。

诊断来源也一并保留：

| 集合与版本 | 规则确认 | 启发式 | 决策树 | 未确认 |
|---|---:|---:|---:|---:|
| 普通 v0.7.0 | 170 | 18 | 32 | 0 |
| 普通 v0.8 候选 | 172 | 11 | 32 | 5 |
| 困难 v0.7.0 | 5 | 25 | 0 | 0 |
| 困难 v0.8 候选 | 5 | 25 | 0 | 0 |

除五例弃答外，9 例从启发式/模型转为规则，2 例从旧规则转为模型；后两例是 `load_boston` / `BaseSettings` 在旧采集记录中的证据边界。其类别没有变化，来源与第一步原文均保留，不能只展示变强的部分。

困难集的 30/30 包括 25 条启发式判断，不能表述为“全部查明并证实”。内置 44 特征树始终未重训，文件摘要与冻结模型相同。

## 4. 大模型结果怎么解释

Qwen3.8 唯一无效回答在 `flat-shop--lm_src_layout`：第一步文字含未转义的双引号，整条不是合法 JSON。即使能人工读懂意图，也按事前解析规则计错，未修补、重发或另报一套更高的“宽松得分”。

困难集中，三个模型都把 NumPy 类型提升和 Pydantic 强制转换场景判为 `code_defect`；登记的注入根因是 `version_incompatibility`。Qwen3.6 和 Gemma 还将 NumPy repr 场景判为代码缺陷；Qwen3.8 在该场景 5/5，但在 PyYAML 场景只对 3/5。

部分类别错误的回答仍提出了具体代码修改，例如将 NumPy 标量显式转成 Python float；本轮没有执行这些建议，不能据类别分数判断它们能否修好。第一步文字的正确性仍标为未评分。

## 6. 输入表示与范围限制

两版 FixFirst 使用同一冻结原始会话；LLM 使用该会话的脱敏白名单表示。本批环境、项目快照与实际出现的 exception/failure/outcome/finish 字段都保留，250 例均未截断。

LLM 没有接收 `run.argv`、FixFirst 的 events/issues 关联、verified_pass/coverage_complete 等派生完整性状态。命令在本批统一带 `-o addopts=`。20 个原会话还有先前规划器保存的 installation_attempts；它们均无执行摘要，不是实际安装记录。离线对照原样保留旧计划，规划器只在内存追加待执行计划，没有读取项目、安装结果、网络或运行新命令。

因此准确说法是**“同一冻结采集证据的两种表示”**，不能声称输入字节或全部上下文完全相同。v0.7.0 重算的主诊断、来源和规则 250/250 与原记录一致；两版最终 500 次重放没有禁止 I/O、额外观测或回放异常。

原普通场景包含模型训练来源，困难案例参与过规则开发；220/30 也不等于 250 个独立真实项目。此处不做未见项目泛化、修复率或显著性声明。旧记录 B3、新采集开发回归、12 个真实项目的人工第一步评分是三份不同证据，不能混成一个成功率。
