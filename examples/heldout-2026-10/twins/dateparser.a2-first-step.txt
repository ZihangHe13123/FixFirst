  The pip log of that run says which part of the command does it.  Every wheel PyPI offers for
  fasttext is a macOS cp27 wheel, so none is usable here; and every source distribution is
  dropped by the flag FixFirst itself sets:

    ERROR: Could not find a version that satisfies the requirement fasttext (from versions: none)

  "No sources permitted" is pip's message for --only-binary=:all:.  fixfirst_command is not the
  only place that flag is set: it is FixFirst's own install policy (src/fixfirst/
  dependency_advice.py:107 and :176, dependency_resolution.py:181, :277 and :285,
  versions.py:146).  No environment variable or pip configuration on this machine forces it:
  no PIP_* variables are set and 'pip config list' prints nothing.

Target failure
  NOT gone.  fasttext is still absent (find_spec -> None) and pytest in the same copy gives
  17 warnings, 3 errors in 9.48 s -- the same collection errors as the original.  The layer the
  label names is not closed by the step FixFirst offers.

  Two things follow, and they matter for how this project is written up:

  1) The flag is the whole difference.  Without it pip does resolve fasttext -- it downloads the
     sdist and tries to build it.  With it there is nothing to resolve at all.

  2) This machine does have a C++ toolchain, and pip finds it.  The build gets as far as invoking
     cl.exe from Visual Studio 2022 Build Tools 14.44.35207; it fails on C++ compile errors in
     fasttext's bundled pybind11 sources (C2672: no matching overload for pybind11::init), not on
     a missing compiler.  twins/dateparser.txt records the first step failing with 'error:
     Microsoft Visual C++ 14.0 or greater is required', which is the message uv's build frontend
     reports; that record was made with 'uv pip install fasttext', so the two runs differ in tool
     as well as in flag.  The Build Tools directory on this machine was created 2026-09-30
     20:37-20:38, about four minutes before that record was written at 20:47.  Whatever the reason
     for the difference, the held-out project was not modified: the label, its scenario and the
     original captures stand as they are, and this note is the record of the discrepancy.
     (For the score it makes no difference -- 'partial' needs only that FixFirst's own step does
     not clear the layer, which is shown above.)
